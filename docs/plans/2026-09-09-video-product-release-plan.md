# 视频功能版本计划：8 小时首版与后续交付

日期：2026-09-09

状态：已暂停并由 [视频业务重做设计](../specs/2026-09-09-video-production-redesign.md) 取代。原 V0.1／V0.2 曾开始部分本地实施，用户随后要求停止代码修改、重新设计业务流程；尚未完成交付。本文工时和分期不再作为新设计的排期依据，保留用于追溯原取舍。

产品目标：小说作者使用即梦／Seedance 2.5，持续制作短剧／漫剧；复用现有设定管理定妆，逐步达到生产级交付。

依据：[产品总规划](../specs/2026-09-09-serial-drama-production-product-plan.md)、[Seedance 2.5 与设定设计](../specs/2026-09-09-seedance-25-lore-visual-production.md)、当前代码 `0a7e701`。工作树已有本任务的规划文档，实施时保留这些改动并重新盘点。

## 1. 版本目标与边界

| 版本 | 用户得到什么 | 完成依据 |
| --- | --- | --- |
| **V0.1：设定定妆与镜头参考** | 在现有角色、地点、道具卡确认单图视觉版本；镜头使用明确版本，换图不覆盖历史 | 约 8 小时实现与验证；开发环境真实持久化和浏览器闭环 |
| **V0.2：Seedance 2.5 单镜试制** | 按定妆生成一个真实可播放镜头，观察状态、选片；异常不会诱导重复付费 | 国内账号、输入与请求适配通过；受控预算内真实供应商与归档恢复验收 |
| **V0.3：系列资产与声音** | 多图定妆、角色声音参考、项目画风版本跨集复用 | 具名新结构验证；同一角色跨集外观与声音验收 |
| **V0.4：分集成片与返工** | 独立分集剧本、跨章来源、多镜生成片段、实际区间映射、整集审片、编辑与延长 | 连续三集及局部返工闭环，真实费用和成果可追溯 |
| **V1.0：生产邀测与商业交付** | 有预算和费用明细、有恢复与支持、有稳定下载的正式产品 | 计费、媒体容量、备份恢复、具名生产迁移和小流量验收完成后逐步开放 |

这里只对 V0.1 设置约 8 小时预算，后续版本在上一版交付后估算，避免把新迁移与真实供应商的不确定性压成没有依据的固定工时。V1.0 的账务与媒体工作在 V0.2 阶段开始设计和验证，不能等到最后才发现生产条件不成立。

## 2. 为什么先做这个版本

当前已有视觉槽、上传素材、权利确认、候选、批准版本和逐镜引用。主要缺口是入口分散、组件与章节分镜耦合，以及引用保护和作者操作说明不完整。

首版把这些已有能力交付成一个能使用的功能：**先在设定里把人物和场景定下来，之后镜头直接引用，不必每次重复建档。** 这同时服务后续图片参考、声音与片段生成。

V0.1 不改模型传输、共享服务协议、渲染任务或数据库结构，避免在 8 小时内同时展开多条高耦合改造。它是按正式代码质量完成的开发版本；生产视频保持当前门禁。

## 3. V0.1 必须交付的功能

### 3.1 在现有设定卡中管理定妆

- 已保存的角色、地点、道具显示“文字设定／视觉定妆”两个页签；不添加尚未实现的声音空页签。
- 未保存的新设定先保存文字，取得真实实体 ID，再允许制作定妆。
- 明确当前视频项目；只有一个 series 项目时默认选择，多个时选择已有项目；无项目时提供显式创建第一个 series 项目的入口。
- 第一版复用现有默认项目参数，不扩展多项目管理产品。项目创建结果不确定时先回读，不自动重复 POST。
- 短篇和生产关闭状态遵守现有规则；读取历史与允许新写入分开判断。

### 3.2 一张图完成一个视觉版本

- 角色支持身份、服装；地点支持场景；道具支持外形。
- 上传图片，作者明确确认素材使用权，填写自然名称、保留特征与排除特征。
- 区分“新建变体”与“为这个变体制作新版”；内部 key 自动管理，不因自然名称相同覆盖其他候选。
- 每个版本一张图，多个服装或场景变体复用现有槽；多角度参考组留待 V0.3。
- 明确显示上传、候选保存、视觉批准的不同状态，不把选择了文件表示为已保存。

### 3.3 作者确认与版本保护

- 同时显示当前正式图和新候选，点击“确认为定妆”后才产生新版。
- 提供紧凑的只读历史图片和版本列表；不做历史一键恢复或复杂对比工具。
- 已绑定镜头继续引用旧版；默认定妆升级不会自动更新镜头或提示词。
- 页面刷新恢复已保存候选和正式版本；未提交的表单通过切换／关闭前提示保护，不在本版承诺跨设备自动草稿保存。
- 409 冲突时显示冲突并回读，保留本地未提交输入，不用新数据静默覆盖作者编辑。

### 3.4 与原视频工作台打通

- 设定入口和视频入口复用同一视觉编辑器与数据读取，避免出现两份定妆状态。
- 在已有正式镜头中选择已确认的身份、服装、场景和道具版本；直接显示图片及版本。
- 切换入口后刷新视觉库，镜头原绑定保持不变。
- 验证现有正式提示词保存链能冻结所选视觉版本及素材哈希；不要求本版触发模型调用来证明该事实。

### 3.5 服务端防止删断来源

- 角色、地点或道具已被视觉槽引用时，后端拒绝物理删除，包括仍有候选的槽。
- 复用现有设定删除错误与引用信息，显示可理解的原因；不新增完整使用关系查询页面。
- 视觉槽创建和删除使用一致的实体锁与事务顺序；验证“先创建引用、后删除”以及“先删除、后创建引用”。
- 兼容既有结构投影；不能因为视频开关关闭就漏查实际仍存在的视觉引用，也不能在没有相应结构的受支持最小上下文中破坏普通设定操作。

## 4. 8 小时工作预算

以下是基于当前代码的估算，包含实施、必要验证和修复，按约 8 小时的工作窗口组织；不是已经测得的完成时间，也不是定时停止后自动算完成。

| 工作 | 预算 | 具体输出 |
| --- | ---: | --- |
| 开工盘点与范围冻结 | 0.5 小时 | 工作树、运行服务、工具链与测试依赖可用；确定组件边界和验收用例 |
| 抽出视觉编辑器并接入设定 | 3 小时 | 两个入口共用；已保存实体、项目选择／首次创建；候选与正式图、变体、紧凑历史列表和离开保护 |
| 镜头绑定与入口间刷新 | 0.75 小时 | 可查看并选择确切参考版本；切换入口不改旧引用 |
| 删除引用保护及定向验证 | 0.75 小时 | 后端引用检查及 PostgreSQL 两种并发顺序验证 |
| 集成、完整必要检查、浏览器验收 | 2 小时 | 前后端检查通过；完整操作记录和截图／结果证据 |
| 修复缓冲与交付整理 | 1 小时 | 修复发现、更新当前需求与交付记录，明确剩余问题 |
| **合计** | **8 小时** | **可演示、可回读、可评审的 V0.1** |

前端编辑器和后端删除保护可以由独立子任务并行推进；整合与验收由同一个负责人收口。并行节省的时间用于修复和验证，不自动增加功能。

### 时间紧张时的取舍

- 优先保留真实候选批准、版本不变、镜头正确引用、服务端删除保护和必要检查。
- 可缩减缩略图排版、装饰和辅助文案；复杂历史对比、完整引用列表和历史恢复本来就不属于本版。
- 最迟约第 5 小时开始集中集成和必要检查，后续停止增加新能力。
- 若删除保护、权限或必要测试仍未通过，明确列为未完成并重新估算；不能通过删掉验收条件让版本看起来准时完成。

## 5. 验收脚本

使用隔离开发数据准备两名角色、一个地点和一件道具；已有的正式镜头方案用固定测试数据准备，不需要付费模型生成。

1. 没有视频项目时，从已保存角色卡创建 series 项目，上传身份图，确认后回读得到 v1。
2. 为角色建立服装变体，为地点和道具建立视觉版本；其他设定不受影响。
3. 上传第二张身份候选，当前 v1 保持不变；刷新后候选仍在。
4. 在原视频工作台给镜头绑定 v1，并通过现有保存路径形成冻结引用；之后批准候选得到 v2，原镜头／提示词仍引用 v1，历史 v1 可浏览。
5. 明确选择 v2 后保存新引用，旧提示词的引用和历史版本仍可读。
6. 切文字／视觉页签不丢文字草稿；切角色／项目和关闭编辑器时正确提示未提交内容；冲突可恢复。
7. 服务端阻止删除有视觉引用的设定，并以 PostgreSQL 验证两种竞争顺序；无引用设定保持原删除行为。
8. 跨用户、跨小说、跨视频项目的读写被拒绝；视频关闭时不能从新入口绕过写入门禁。

“素材已在本地批准”与“供应商允许接收该素材”不混淆。V0.1 不显示“已通过 Seedance 人像认证”等未经实现的状态。

### 必要验证

- 相关前端状态与交互测试、`npm run typecheck`、`npm run lint`。
- Java 相关 JUnit、真实 PostgreSQL Testcontainers 并发与归属验证、提交前 `./mvnw verify`。
- 浏览器执行上述核心流程；记录已保存状态、真实返回版本及历史引用。
- 本版预期不修改公共 DTO 或 Python；若实施发现必须改变公共接口，先调整规格、生成客户端并执行相应 `api:check` 与 Python 检查，同时重估工作量。

验证结果必须区分计划、已执行、通过与待处理；不能将现有测试文件存在写成这次测试已通过。

## 6. 本版实施点与依赖

主要实施点：`lore-panel.tsx`、`visual-canon-panel.tsx`、视觉状态辅助、`chapter-adaptation-workspace.tsx` 的项目上下文复用、`JooqLoreRepository` 的删除检查及相关测试。新文件以独立单设定视觉编辑器和项目上下文辅助为主；不重写整个设定管理器或视频工作台。

开工前读取 `DESIGN.md`、产品基线及相关 Java 基线／架构决策。检查当前依赖可用；本机 Homebrew git 曾缺少 pcre2 库，可使用 `/usr/bin/git`，不把修复全机环境作为功能范围。

8 小时估算假设 Node 依赖、JDK 21、Maven、Docker／隔离 PostgreSQL 可用。环境安装、全量测试新暴露的基线故障可能影响工期，应尽早暴露并报告，不能静默跳过。

V0.1 不需要 Seedance API Key、真实生成预算或新数据库迁移。V0.2 才需要可调用的国内模型、供应商认可的素材、可访问的参考地址及明确测试额度。若这些未就绪，不能把 fake 验收描述为真实试制成功。

## 7. V0.2 之后的关键交付条件

- V0.2 先校准窄的单镜图片参考模式；新建请求按当前 2.5 规则校验，历史 2～3 秒冻结清单继续可读，不全局收紧旧 manifest。首尾帧及完整多模态另按具体场景接入。
- 真实付费试制之前，修复持续观察、提交未知与归档恢复；供应商成功后的下载失败必须恢复原任务，不新建生成收费。受控试制以人工确认额度和账单留证，不能扩为公开自助收费。
- V0.3 的多图、声音、画风和来源快照，以及 V0.4 的跨章／多镜片段，均先设计公共契约与具名迁移。外貌或声音固定仍是输入依据，输出质量须实测。
- 公开收费前，报价、预算预留、结算、补偿和对账必须全闭环；公开生产前完成媒体工作空间、原片／代理、备份恢复、支持流程和既有门禁要求。
- V1.0 继续以“目标作者连续完成三集并中途局部返工”为产品验收，不降低前两份规划的最终目标。

## 8. V0.1 最终交付物

可运行的代码变更、必要测试、开发浏览器演示、变更与验收记录，以及按实际实现更新的相关需求文档。保持数据库结构和生产开放状态的现有边界；不将新增页签描述为视频产品已经生产上线。
