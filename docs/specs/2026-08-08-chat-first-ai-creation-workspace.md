# AI 创作模块聊天优先重构规格

状态：已确认，待实施

日期：2026-08-08

## 背景

长篇小说的 AI 创作模块原本以写作会话为核心：用户通过连续聊天提出讨论、规划、写作、返工、审核和设定维护请求，系统自动识别 CreativeOperation、选择 Agent、生成待审核 Artifact，并允许用户刷新或重新进入页面后恢复消息和未完成任务。

当前页面虽然仍保留 `WritingSession`、`WritingMessage`、任务恢复和 SSE，但产品表达已经偏离该目标：

- “规划本章、生成正文、重写场景、审核追读、检查 OOC”以五个平级任务按钮占据聊天上方，聊天看起来像功能执行日志；
- 运行状态、聊天消息和 Artifact 审核分别占据顶部状态、中央消息区和右侧审核栏，用户难以把它们理解成一次连续协作；
- Artifact 主要从任务单独收集到右栏，不能稳定作为历史时间线中的产物节点恢复；
- 当前任务可以从 LangGraph 快照恢复，但任务完成后在同一会话继续发送消息会创建新任务，新任务只以本次用户消息初始化 `conversationHistory`，没有继承该会话此前可见对话，形成“页面恢复了、模型上下文没有恢复”的语义断点。

本次重构恢复聊天优先的原始产品模型：聊天是唯一主入口，流程是后台约束和消息状态，不是另一套页面导航。

## 目标

1. 以可恢复的聊天时间线承载全部 AI 创作任务。
2. 将运行状态、Agent 流式输出、Artifact、审核结论和正式写入回执表达为时间线中的稳定节点。
3. 保留右侧区域，但将其收敛为当前所选 Artifact 或任务卡的检查器，不再承担独立流程导航。
4. 所有长耗时 AI 操作先返回可追踪任务，再通过 SSE 持续展示进度，避免用户面对空白页面等待。
5. 刷新、断流和重新进入会话后，恢复完整可见消息、当前任务、当前 Artifact 和可继续操作。
6. 修复同一会话跨任务的模型上下文断裂，使新任务获得该会话此前可见对话。

## 非目标

- 不引入步骤向导、固定流水线页面或独立的“规划/写作/审核”功能页。
- 不取消自然语言分类、CreativeOperation、五个 Agent 或 ReviewArtifact 状态机。
- 不允许 Agent 绕过 ReviewArtifact 直接写入正式小说数据。
- 不修改 PostgreSQL schema；允许使用现有 `WritingMessage.metadata`、任务、命令和 Artifact 数据表达关联。
- 不把每个 SSE token 或临时状态持久化为一条数据库消息。
- 不新增移动端方案；继续遵循 PC 优先。
- 不给 Agent 聊天正文增加 Markdown 渲染。

## 产品原则

### 聊天是唯一主入口

用户通过输入自然语言完成讨论、规划、写作、返工、审核、设定更新和进度整理。系统可以推荐下一句话，但推荐项只是输入辅助，不是独立模块，也不能绕开消息与任务的统一入口。

### 流程是消息状态

“已受理、正在识别、Agent 工作中、复审中、待确认、应用中、已应用、失败”均围绕当前消息或任务卡表达。页面不再用一个与聊天分离的步骤条驱动用户。

### SSE 负责实时体验，Core 负责权威状态

SSE 事件即时更新界面，但不能成为完成、失败或正式写入的唯一事实来源。断流、刷新或重连后，前端必须查询 Core 的任务、命令、Artifact 和 `run_outcome` 对账。

### Artifact 是聊天产物，不是旁路数据

Beat Plan、正文、设定更新和其他待审核产物必须在产生它们的对话位置形成稳定消息卡。右侧检查器只展示选中卡片的完整内容、Diff、来源状态、评审结论和决定控件。

## 页面结构

### 左侧：章节导航

保留章节列表，展示章节标题、字数和正式状态。当前章节可以补充一行简短的会话状态，例如“计划待确认”或“正文生成中”，但不在左栏放置 Artifact 决策按钮。

### 中央：会话时间线

中央区域包含：

1. 会话头部：章节标题、当前会话标题、消息数量、自动保存状态、历史对话和新对话入口；
2. 恢复提示：重新进入页面时说明恢复了哪个会话、多少条消息以及当前任务停留状态；
3. 消息时间线：用户消息、Agent 最终回复、实时 Agent 消息、运行卡片、Artifact 卡片和稳定结果回执；
4. 输入区：自由输入始终是主操作，推荐说法以轻量 chip 放在输入框上方。

移除聊天上方五个平级的“创作任务”按钮。现有 `composeWritingTaskActions()` 可以继续提供推荐逻辑，但结果只能作为输入区的推荐说法，点击后仍按普通消息发送。

### 右侧：上下文检查器

右侧不再称为独立“审核与确认”流程栏，改为上下文检查器：

- 未选中任务卡时显示当前章节的正式上下文摘要，不提供另一组工作流按钮；
- 选中运行卡时显示当前 Operation、Agent、阶段和可恢复状态；
- 选中 Artifact 卡时完整展示候选、Diff、来源绑定、revision、评审结论和写入影响；
- 只有在完整候选已成功读取且 Artifact 仍为可决定状态时，显示批准、返工和丢弃控件。

Artifact 决定仍由右侧检查器提交，时间线卡片只提供“查看完整内容、继续讨论、要求返工”等入口。不得让用户在未查看完整内容和写入影响时执行模糊的一键批准。

## 时间线消息模型

前端将时间线项目区分为以下展示类型：

| 类型 | 来源 | 持久化与恢复 |
| --- | --- | --- |
| 用户消息 | `WritingMessage(role=user)` | 完整持久化并按顺序恢复 |
| Agent 最终回复 | `WritingMessage(role=agent)` | 完整持久化并按顺序恢复 |
| Agent 实时消息 | SSE `agent_start/status/chunk/done` | 运行期间内存更新；最终回复持久化后替换 |
| 运行卡片 | 202 受理结果、SSE、`currentTask`、`run_outcome` | 当前运行从任务和命令重建；稳定终态可由消息 metadata 和任务结果恢复 |
| Artifact 卡片 | Artifact SSE、任务 activeArtifactId、ReviewArtifact | 保存或重建稳定 `taskId/artifactId/revision` 关联，重新读取 Core 权威 Artifact |
| 写入回执 | Artifact 决定命令与权威 outcome | 以稳定终态消息或任务结果恢复，不依赖旧 SSE 事件 |
| 错误卡片 | 请求错误、任务错误或对账错误 | 稳定错误从任务和命令恢复；临时断流不生成失败卡 |

运行中多个状态更新必须修改同一张运行卡片，禁止把每个 `agent_status`、工具调用或复审步骤刷成独立聊天消息。工具调用详情继续默认隐藏在流程日志或调试区域。

## SSE 交互设计

### 首次发送

1. 用户点击发送后，前端立即把用户消息加入时间线并清空输入框；该视觉反馈不等待网络。
2. Core 返回 202、taskId 和 commandId 后，时间线创建或绑定一张运行卡片，显示“请求已受理，正在分配 Agent”。
3. 前端立即连接 `/api/v1/writing/runs/{taskId}/events`。
4. `operation_classified`、`operation_stage`、`agent_start`、`agent_status`、`agent_chunk`、`artifact_review_started` 等事件持续更新当前运行卡和实时 Agent 消息。
5. `artifact_awaiting_user_approval` 到达后，当前运行卡稳定为 Artifact 卡片，并从 Core 读取权威 Artifact。
6. `run_outcome.streamShouldClose=true` 时关闭当前连接；完成、失败和等待用户均以权威 outcome 收口。

### Artifact 决定

1. 用户在检查器中提交批准、返工或丢弃。
2. 接口返回 202 后，原 Artifact 卡立即进入“应用中”或“返工中”，并重新连接返回 taskId 的 SSE。
3. 前端不得再次调用普通 resume，也不得乐观宣称正式写入成功。
4. 收到权威 outcome 后，将卡片稳定为已应用、返工后的新 revision、已丢弃或失败。

### 断流与重连

- 复用现有事件游标和 `Last-Event-ID`，从最后确认的事件后续传；
- 保留现有短退避自动重连，并在卡片上显示“连接中断，正在重新连接”，不把任务标为失败；
- 每次流结束或连接失败后查询运行状态，使用 Core `run_outcome` 判断是否继续连接；
- 用户刷新页面后先恢复会话、消息、currentTask 和 Artifact，再继续连接仍未收口的任务；
- SSE 中断不等于取消，取消必须使用显式取消操作。

## 会话恢复与上下文连续性

### 页面恢复

选择历史会话时，前端按顺序恢复全部可见 `WritingMessage`，同时读取 `currentTask`、`lastTask` 和活动 Artifact。恢复提示必须明确说明：

- 恢复的会话名称；
- 已恢复消息数量；
- 当前是否存在活动任务；
- 是否有待确认 Artifact；
- 下一步是继续接收 SSE、等待决定，还是允许发送新消息。

### 当前任务继续

对于 `active`、`waiting_call` 或 `awaiting_user_review` 的当前任务，普通后续消息继续调用该 task 的 resume，保持原 LangGraph 快照与 `conversationHistory`。

### 同一会话的新任务

历史任务终态后，用户在同一会话继续发送消息会创建新任务。Core 创建该任务时必须从同一 `WritingSession` 读取此前可见的用户和 Agent 消息，按时间顺序组装新任务的初始 `conversationHistory`，再追加本次用户消息。

要求：

- 不只恢复前端显示而忽略模型上下文；
- 不从工具日志、调试内容或完整 Artifact 正文反推聊天历史；
- 不静默截断用户消息或 Agent 可见回复；如果完整会话超出模型可接受上下文，必须明确失败或进入后续单独设计的显式摘要机制，本次不伪装为完整恢复；
- 新任务仍绑定原 writingSessionId，方便随后恢复和审计。

## Artifact 审核

### 时间线卡片

卡片展示：

- 产物类型和标题；
- 当前状态和 revision；
- 简短摘要；
- 来源绑定状态；
- Reviewer 结论；
- 正式写入目标；
- “查看完整内容”主入口。

### 检查器

检查器必须完整展示正文、Beat Plan、结构化更新、Diff 或删除影响，不得静默截断。文本草案继续允许本地编辑并在 approve 时提交完整 `editedContent`；Beat Plan 不允许用该字段修改，结构性变更必须走 revise。

### 历史恢复

时间线中的 Artifact 卡保存稳定关联而非旧候选快照。重新打开会话时使用 artifactId 向 Core 读取当前权威状态：

- awaiting_user：恢复决定入口；
- applied：显示已应用回执，不重新开放操作；
- deleted/discarded：显示已丢弃；
- revision 已变化：显示最新 revision，并保留该对话节点的返工关系。

## 错误与空状态

- 请求尚未收到 202：用户消息保留，显示“正在提交”；明确失败后提供重试，重试必须复用稳定 clientRequestId 或按现有幂等规则对账。
- SSE 暂时中断：显示重连状态，不显示错误卡。
- 权威任务失败：时间线形成错误卡，展示用户可理解的原因和可执行重试入口；详细 requestId 和错误码放在展开区域。
- Artifact 读取失败：保留卡片身份，显示“内容暂时无法读取”，禁止批准。
- 会话为空：仅显示简洁引导和输入框，不用五张任务卡占据首屏。
- 无待确认 Artifact：右侧展示当前章节上下文，不展示大面积虚假的流程空状态。

## 数据与架构影响

### Web

- 重组 `WritingConversation` 的展示边界，将任务动作栏、消息流、实时 Agent 状态、Artifact 卡和右侧检查器统一为时间线模型；
- 将 `product-actions.ts` 的结果从顶部平级按钮改为输入框附近的推荐说法；
- 增加可从消息、任务和 Artifact 组合得到的时间线投影；
- 保留现有 SSE 解析、游标、重连和 outcome 对账能力，调整其 UI 投影，不重新发明第二套流监听器；
- 拆分过大的 `writing-conversation.tsx`，至少分离时间线投影、运行卡、Artifact 卡、检查器和会话恢复提示，避免继续在单文件堆叠状态分支。

### Core API

- 不修改数据库 schema；
- 同一会话创建新任务时，从现有 `WritingMessage` 组装初始会话历史；
- 使用现有消息 metadata 或可确定查询关系保存稳定 task/artifact 关联；
- 公共 API 如发生契约变化，先修改 Pydantic 契约并重新生成 TypeScript 客户端。

### Agent Service

本次不改变 CreativeOperation、Agent 职责、LangGraph 状态机或 ReviewArtifact 决策规则。Agent Service 继续接收 Core 提供的任务会话历史和运行上下文；若 Core 扩展会话历史组装，只需验证现有状态契约能够完整接收。

## 测试要求

### Web

- 会话初始化恢复消息、当前任务和活动 Artifact；
- 用户发送后立即出现消息和运行卡，不等待 SSE；
- 多个 SSE 状态更新只修改同一运行卡；
- `agent_chunk` 流式更新，最终持久消息到达后正确替换临时消息；
- Artifact SSE 生成时间线卡，点击后检查器读取完整权威内容；
- Artifact 决定 202 后进入进行中状态并继续监听；
- SSE 断流、重连、游标续传和 outcome 对账；
- 刷新后 awaiting/applied/discarded Artifact 的正确恢复；
- 顶部五个任务按钮不再出现，推荐说法仍通过普通聊天请求执行。

### Core API

- 创建新任务时，同一 session 的历史用户和 Agent 消息按顺序进入 `conversationHistory`；
- 本次用户消息只追加一次，不重复；
- 不同小说、章节、用户或 session 的消息不能串入；
- 当前任务 resume 继续使用原图快照，不重复组装历史；
- Artifact、任务和消息稳定关联能够在刷新后查询；
- 不修改数据库结构指纹。

### 回归

- ReviewArtifact approve/revise/discard 状态机不变；
- 正文、Beat Plan 和 agent_updates 的正式应用规则不变；
- 中短篇专用操作不进入长篇多 Agent 工作流；
- 当前 SSE 严格事件契约、重连和 `run_outcome` 终态对账继续通过；
- `npm run typecheck`、`npm run lint`、相关 Web 测试、Core pytest、Ruff 和 Mypy 通过。

## 验收标准

1. AI 创作页首屏以聊天和输入框为主，不再显示五个平级功能模块。
2. 用户发送消息后立即看到自己的消息和可追踪运行状态，模型执行期间持续收到 SSE 反馈。
3. 所有任务仍由自然语言消息发起，推荐说法点击后也走相同消息入口。
4. 规划、正文、设定变更和其他 Artifact 在原对话位置显示为稳定卡片。
5. 右侧仅作为选中卡片的检查器，完整展示候选、Diff、来源、评审和写入影响。
6. 批准、返工或丢弃后继续通过 SSE 显示处理过程，并由权威 outcome 收口。
7. SSE 断开时用户看到重连状态，任务不会被误报为失败或取消。
8. 刷新或重新进入会话后，消息、当前任务和 Artifact 均可恢复。
9. 同一会话创建的新任务能够获得此前可见聊天历史，模型上下文与用户看到的历史一致。
10. 不新增数据库表或字段，不改变正式内容必须经 ReviewArtifact 批准的边界。
