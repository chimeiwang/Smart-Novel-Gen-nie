# 阿里云手机号认证规格

状态：正式库具名迁移与生产启用已完成；真实浏览器验证码核验和自动建号仍待用户验收

日期：2026-08-27

## 1. 背景

InkForge 当前只支持用户名密码注册和登录。浏览器会话由 Core 签发 30 天 HS256 JWT，并写入
`inkforge-token` HttpOnly Cookie；Redis 负责认证限流，`User.username` 与 `User.passwordHash` 均为非空。
Java Core 已于 2026-08-26 接管生产并仍处于观察期。用户于 2026-08-27 批准按本规格实施手机号认证，并于
同日进一步批准具名迁移只对服务器端 `novelwriterdev` 开发库执行。当前工作树已完成公共契约、Java 供应商
适配、Redis 状态机、事务自动建号、Web 流程和隔离数据库测试。服务器开发库已完成备份、两次幂等迁移、
真实结构契约导出和只读复核。用户随后确认重庆市创煜新软件有限公司为运营及个人信息处理主体，并提供
`niebqoiang@gmail.com` 作为用户协议和隐私政策的公开联系邮箱。用户于同日进一步明确批准：备份后对服务器端
`novelwriter` 正式库执行具名脚本 `scripts/migrations/20260827_user_phone_identity.sql`，并开启生产手机号登录
与真实短信发送。该授权不包含其他生产 DDL、老账号自动绑定、账号合并或删除原用户名密码登录。

## 2. 目标

- 为桌面 Web 提供一个中国大陆手机号短信验证码入口；
- 手机号已有账号时直接登录，没有账号时在验证码通过后自动创建并登录；
- 新用户不再填写用户名和密码，登录页必须在发码前明确说明“未注册手机号验证后将自动创建账号”；
- 已有用户名密码账号继续使用原登录方式，不要求绑定手机号；
- 使用阿里云完成真人校验、验证码生成、发送、生命周期管理和核验；
- 继续由 Core 独占账号、积分、会话、限流和数据库写入；
- 不向浏览器、Next.js 服务端或 Python Agent 暴露阿里云 AccessKey；
- 通过独立开关受控启用生产能力，并保留关闭开关但不删除手机号身份数据的回滚路径。

## 3. 非目标

- 首期不做 iOS、Android、HarmonyOS 原生一键登录；
- 不接入 H5 本机号码校验，不要求用户关闭 Wi-Fi 或切换移动网络；
- 不支持国际、港澳台手机号，首期国家码固定为 `+86`；
- 不把手机号当作公开用户名，不在 URL、日志、错误或分析事件中输出完整手机号；
- 不做老账号手机号绑定、邮箱、微信、OAuth、账号合并、手机号注销、无密码 CLI 登录或管理员账号管理；
- 不删除用户名密码登录，不改变现有 Cookie 名称、JWT claims 和 30 天有效期；
- 不根据姓名、用户名、设备、来源 IP 或其他弱证据把手机号自动关联到已有老账号；
- 不使用通用短信服务 `Dysmsapi.SendSms`；号码认证赠送签名和模板不能与通用短信资源混用；
- 不在应用启动时自动建表或迁移数据库。

## 4. 阿里云产品选择

### 4.1 短信认证

首期使用阿里云号码认证服务 PNVS（`Dypnsapi`）的短信认证能力：

- `SendSmsVerifyCode`：由阿里云动态生成并发送验证码；
- `CheckSmsVerifyCode`：由阿里云核验手机号、验证码和有效期；
- Java SDK：`com.aliyun:dypnsapi20170525:2.0.0`；验证码 SDK 为
  `com.aliyun:captcha20230305:1.2.0`；
- Endpoint：`dypnsapi.aliyuncs.com`；
- 登录/注册优先使用平台赠送且相互匹配的签名和模板，生产值从部署密钥或配置读取；
- 禁止配置返回明文验证码，禁止传入由 InkForge 自行生成的固定验证码，否则阿里云无法完成核验闭环。

该能力适用于 Web，且把验证码生命周期交给供应商，减少 Core 内自建 OTP 状态机。供应商成功只证明手机号
验证通过，不能直接签发 InkForge 会话；Core 仍必须完成挑战校验、账号查找或自动建号事务后才能设置 Cookie。

### 4.2 人机校验

所有未登录的短信发送请求先使用阿里云验证码 2.0 Web 场景：

1. Web 按阿里云 V3 架构动态加载官方验证码脚本；
2. 浏览器取得不透明的 `CaptchaVerifyParam`；
3. Core 调用 `VerifyIntelligentCaptcha` 完成服务端复核；
4. 只有复核成功且本地限流通过后，Core 才调用 `SendSmsVerifyCode`。

`CaptchaVerifyParam` 只能原样透传，不记录正文，不允许 Web 自报“已验证”。生产手机号发码默认强制人机
校验，不能因为手机号曾经成功登录就绕过。

### 4.3 暂不选择号码认证一键登录

原生一键登录主要面向移动 App。H5 能力受移动数据网络、运营商、双卡和页面交互限制，不适合作为当前
桌面优先 Web 的主登录路径。未来出现原生 App 时，应另立 spec，再评估融合认证或一键登录。

## 5. 产品流程

### 5.1 统一手机号登录和自动注册

1. 登录页默认展示“手机号登录”，并与“原账号登录”形成清晰的双入口；页面说明“未注册手机号验证后将自动
   创建账号”，用户勾选当前版本的用户协议与隐私政策；用户协议和隐私政策必须是未登录状态可直接访问的
   公开页面，不能被会话路由保护重定向；
2. 用户输入 11 位中国大陆手机号并完成人机校验；
3. Core 规范化为 E.164 `+86...`，执行来源和手机号双维度限流；
4. Core 创建一次性挑战并调用阿里云发送验证码；
5. 用户提交手机号、挑战 ID 和验证码；
6. Core 校验挑战绑定和尝试次数，再调用阿里云核验；
7. 核验成功后，Core 查询唯一手机号身份：存在则直接签发既有会话 Cookie；
8. 手机号身份不存在时，Core 在同一 PostgreSQL 事务中创建 `User`、手机号身份和唯一注册奖励，提交后签发
   同一种会话 Cookie；
9. 挑战原子消费，重复提交或并发挑战不能创建第二个账号、重复发奖或产生孤立 `User`。

手机号是否已注册不会在发码阶段披露。核验接口对已存在和新建账号使用同一成功响应结构，只通过
`isNewUser` 告知当前用户本次是否新建，以便首次进入工作台时显示欢迎信息。

### 5.2 老账号边界

迁移前的用户名密码账号没有手机号事实，系统无法安全推导关联关系。它们继续通过用户名密码登录；登录页不再
展示用户名注册入口。“原账号登录”必须在同一页面直接可见，不得要求老用户先绑定手机号或经过找回流程。
老用户如果主动使用一个从未登录过的手机号，会按上述流程获得一个新的独立账号，旧账号中的作品、积分、文风
和任务不会迁移、共享或自动合并。页面必须在手机号入口附近明确提示这一点。

新手机号账号不设置用户可知的用户名或密码，因此首期不能使用现有 CLI。后续若需要找回旧账号、合并账号、
设置密码或让手机号账号使用 CLI，必须分别立项并建立强身份校验，不能靠人工猜测归属。

### 5.3 供应商不可用

- 阿里云发送或核验不可用时，手机号路径返回稳定的 503 错误，用户名密码登录继续可用；
- 发送请求出现超时或结果不明时不自动重试，防止同一次点击产生多条短信；
- 结果不明的挑战进入冷却时间，用户只能在提示时间后重新发起；
- 核验没有得到阿里云明确成功响应时，Core 绝不创建用户或签发会话；
- readiness 只检查启用后的必需配置和本地协作者，不用真实发短信探活，不因供应商瞬时故障阻断整个 Core。

## 6. 公共接口

接口已先进入公共 Pydantic 契约，再生成 Java 接口与 TypeScript 客户端；Python 回滚镜像保持同形、默认
关闭的稳定错误响应。

### 6.1 创建挑战

`POST /api/v1/auth/phone/challenges`

请求：

```json
{
  "phone": "13800138000",
  "captchaVerifyParam": "阿里云返回的不透明参数",
  "consentVersion": "当前协议版本",
  "acceptedTerms": true,
  "clientRequestId": "稳定请求标识"
}
```

只有明确接受当前协议版本才可创建挑战。成功响应只返回随机 `challengeId`、`expiresInSeconds` 和
`resendAfterSeconds`，不返回验证码、完整手机号、供应商 BizId 或账号存在性。

### 6.2 核验、登录或自动创建账号

`POST /api/v1/auth/phone/challenges/{challengeId}/verify`

请求包含与挑战匹配的 `phone`、用户输入的 `code` 和稳定 `clientRequestId`。核验成功后，已存在账号直接
登录；新手机号在同一事务中自动建号并发放一次注册奖励。两种情况统一返回 `PhoneLoginResponse` 并设置
Cookie，响应包含现有用户字段、可空 `maskedPhone` 和 `isNewUser`，不返回完整手机号、密码哈希或供应商凭据。

### 6.3 兼容性

- 现有 `/auth/login`、`/auth/logout`、`/auth/me` 保持可用，供老账号继续登录；
- Web 下线用户名密码注册入口；`/auth/register` 在迁移兼容期保留代码但由生产配置关闭，后续删除需单独批准
  公共契约变化；
- `UserResponse` 不返回完整手机号；新增可空 `maskedPhone`，只能形如 `138****8000`；
- CLI 继续只支持老账号的用户名密码，不接入短信交互；
- Next.js 仍不新增业务 API、Server Action 或阿里云服务端 SDK。

## 7. 数据与状态

### 7.1 PostgreSQL 具名迁移

`scripts/migrations/20260827_user_phone_identity.sql` 新增独立 `UserPhoneIdentity`，不把手机号塞进公开
用户名，也不改变 `User.passwordHash` 的非空约束：

| 字段 | 约束 | 用途 |
| --- | --- | --- |
| `id` | `TEXT` 主键 | 稳定身份 ID |
| `userId` | `TEXT`、唯一、外键到 `User.id` | 每个用户最多一个手机号 |
| `phoneE164` | `TEXT`、唯一、检查 `^\\+861[3-9][0-9]{9}$` | 规范化登录标识 |
| `verifiedAt` | 非空时间 | 最近一次确认归属的事实 |
| `consentVersion` | 非空文本、最长 64 字符 | 自动建号时接受的协议版本 |
| `consentedAt` | 非空时间 | 自动建号时的同意时间 |
| `createdAt` | 非空时间 | 创建审计 |
| `updatedAt` | 非空时间 | 身份记录变更 CAS 基线 |

迁移创建的 `UserPhoneIdentity` 必须与现有 `User` 表属于同一数据库角色。该所有权是生产应用读取、写入手机号
身份表的最小运行契约；即使迁移由 PostgreSQL 管理账户执行，也必须在同一事务内对齐所有者并在后置条件中复核，
不得依赖超级用户运行应用或授予全库权限。

手机号属于个人信息。业务查询、异常、指标和结构化日志必须默认脱敏；数据库备份沿用加密和受控访问。若后续
决定对手机号列做应用层加密，必须同时解决确定性查询、密钥轮换、唯一性和灾难恢复，不能只做不可查询的
表面加密。

用户已经批准起草 `scripts/migrations/20260827_user_phone_identity.sql`、在隔离 PostgreSQL 验证幂等，并
先批准该具名脚本只对服务器端 `novelwriterdev` 开发库执行；随后又明确批准备份后对正式库 `novelwriter`
执行同一具名脚本并启用生产手机号真实发送。执行前必须备份，执行后必须重复运行验证幂等，并从真实数据库
只读核对契约。正式库必须额外提供精确确认令牌；该授权不包含其他远程数据库 DDL。

服务器开发库执行结果：迁移前备份归档及 SHA-256、`pg_restore --list` 校验通过，SQL 连续执行两次均成功；
迁移后表为 8 个预期字段、7 个预期约束和 0 行初始数据。真实 `novelwriterdev` 导出的完整 contract 共 86 张
表，指纹为 `4f8cbf58820c7e601026012249f1896e4f8ad0231cfa6b9bd2fdad1c83c3d195`，再次只读核验为零差异。

真实开发库导出的完整 contract 必须包含 `UserPhoneIdentity`。为允许生产先部署关闭开关的兼容镜像，Python
与 Java 的 schema guard 在 `PHONE_AUTH_ENABLED` 和 `PHONE_AUTH_SEND_ENABLED` 未同时为 `true` 时，只从
期望与实时结构中精确投影掉这一张手机号表；其他结构漂移仍须失败。两个开关同时开启时不得投影，readiness
必须强制正式库已经存在完整手机号身份结构，不能靠关闭结构校验绕过生产迁移。

为兼容现有非空 `User.username/passwordHash` 和旧版本回滚，新手机号账号使用不含手机号的随机内部用户名，
并保存一个由服务端随机生成、从未向任何人返回且立即丢弃原文的高熵密码之 BCrypt 哈希。两者只是旧结构兼容
占位，不能作为用户可操作的登录名展示或用于找回。公共契约为兼容旧客户端可以继续返回该不透明
`username`，但 Web 必须优先展示 `maskedPhone`。若后续决定把这两个旧字段改为
可空，必须另立结构规格并完成全部 Web、CLI、回滚和契约影响分析，不能在本次迁移中顺手扩大范围。

### 7.2 Redis 挑战

Redis 只保存短期挑战状态，不保存明文验证码：

- 随机挑战 ID、规范化手机号的 HMAC-SHA-256 摘要和协议版本；
- 供应商 `outId`/BizId、创建和过期时间；
- 发送状态、核验失败次数、消费状态和 `clientRequestId` 幂等结果。

挑战建议 5 分钟失效，短信最短重发间隔 60 秒，单挑战最多 5 次核验。Redis 不可用时认证失败关闭；不能
绕过挑战直接调用阿里云或写 PostgreSQL。

## 8. 防刷与安全

本地与阿里云控制台同时限流，任一层拒绝都不继续发送。来源额度在人机验签前计数以保护供应商接口；手机号
额度只在人机验签成功后计数，避免无效验证码请求恶意耗尽目标手机号额度：

- 同手机号默认每 60 秒 1 条、每小时最多 5 条、每自然日最多 10 条；
- 同来源默认每分钟最多 5 条、每小时最多 20 条、每天最多 50 条，避免攻击者轮换手机号；
- 发送、核验和自动建号分别计数，失败核验不能无限尝试；
- 限流键只使用手机号摘要和可信来源摘要，不把完整手机号写入 Redis key；
- 阿里云控制台开启发送频率、日/月费用上限和联系人预警；
- 认证响应在核验成功前不披露手机号是否已有账号；
- 密码、短信验证码、`CaptchaVerifyParam`、AccessKey Secret、Cookie、JWT 和完整手机号不得进入
  日志、Sentry、分析事件、OpenAPI 示例或测试快照；
- Cookie 继续保持 `HttpOnly`、`SameSite=Lax`、生产 `Secure`；手机号登录不降低现有会话安全属性。

## 9. 凭据与配置

阿里云主账号 AccessKey 禁止进入应用。生产使用独立程序身份，人与程序分离，并按最小权限授予至少以下
调用能力：

- `dypns:SendSmsVerifyCode`；
- `dypns:CheckSmsVerifyCode`；
- 验证码 2.0 服务端核验所需权限。

在阿里云支持的权限条件下限制生产出口 IP；短信认证与人机校验可使用分离的 RAM 程序身份，避免一个凭据
获得无关管理权限。AccessKey Secret 只能通过受控部署环境或等价凭据提供链注入，环境文件必须受宿主机
权限保护，不能提交到仓库、写入镜像或输出到进程日志。

实现已冻结以下配置名：

- `PHONE_AUTH_ENABLED=false`：总开关；
- `PHONE_AUTH_SEND_ENABLED=false`：真实短信发送开关；
- `USERNAME_REGISTRATION_ENABLED=true`：兼容部署先保持现状，手机号全量开放时生产显式改为 `false`；
- `PHONE_AUTH_HMAC_SECRET`、`PHONE_AUTH_CONSENT_VERSION`、`PHONE_AUTH_REDIS_PREFIX`；
- `ALIYUN_ACCESS_KEY_ID` / `ALIYUN_ACCESS_KEY_SECRET`；
- `ALIYUN_PNVS_SIGN_NAME`、`ALIYUN_PNVS_TEMPLATE_CODE`、`ALIYUN_PNVS_SCHEME_NAME`；
- `ALIYUN_CAPTCHA_PREFIX`、`ALIYUN_CAPTCHA_SCENE_ID`；
- 开发与生产必须使用分离的 HMAC 密钥和 Redis 前缀。

生产缺少必需配置时，总开关不得开启；测试模式使用显式 fake provider，禁止读取开发者真实 AccessKey。

## 10. 阿里云控制台准备清单

以下操作会产生外部状态或费用，需由账号所有者执行或另行明确授权；本次生产迁移与真实发送已获得上述具名
授权，其他供应商配置变更仍不自动获得授权：

1. 完成阿里云账号实名认证并开通号码认证服务的“短信认证”；
2. 从只读列表记录平台赠送的登录/注册签名和模板，并在 API 参数中传入匹配的签名名称与模板 Code；控制台
   不存在持久化“选择”按钮；
3. `SchemeName` 可暂留空使用阿里云默认方案；若后续填写，发送和核验必须使用完全相同的值；
4. 开通验证码 2.0，创建 Web 场景，先使用测试策略验链，生产前切为正式策略；
5. 创建独立 RAM 程序身份，禁用控制台登录，授予最小 API 权限并限制来源；
6. 购买小额测试包或启用按量付费，设置日/月限额、余额和异常量预警；
