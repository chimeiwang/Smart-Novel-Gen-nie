# 视频开发预览闭环加固

## 状态

- 日期：2026-08-17
- 状态：补充加固已完成；代码、服务器 dev 数据库与浏览器真实流程均已验证
- 数据目标：本地服务连接的服务器端 `novelwriterdev`
- 生产边界：不得连接或修改生产数据库；生产环境必须在视频预览关闭时完全忽略 dev 专用结构

## 问题

当前视频批准命令已经能保存 `clientRequestId` 和首次结果，但仍有四个闭环缺口：

1. 数据库只能分别确认用户、场景、候选和任务存在，不能证明它们属于同一小说、项目和场景；
2. schema contract 尚未采集 PostgreSQL `CHECK` 约束，约束被手工删除时结构守卫无法发现；
3. 生产关闭视频预览后仍会装配视频 dispatcher，并用包含 dev 视频表的完整契约检查生产数据库；
4. 批准并发语义只有模拟会话测试，没有在真实 `novelwriterdev` 上使用独立事务验证和自动清理测试数据。

此外，部署脚本在 macOS 测试环境中使用 GNU 专属 `stat -c`，部分 Bash 变量后紧跟中文标点，在
`set -u` 下会被错误解析。

## 实施约束

### 数据库一致性

扩展具名迁移 `scripts/migrations/20260817_video_review_decision_command.sql`，为批准命令增加
`projectId`、`novelId`，并通过组合外键建立完整归属链：

```text
requestedByUserId <- Novel(id, userId)
novelId           <- VideoProject(id, novelId)
projectId         <- VideoScene(id, projectId)
sceneId           <- ReviewArtifact(id, videoSceneId)
sceneId/projectId <- VideoGenerationTask(id, sceneId, projectId)
```

已有命令先从 Scene、Project 回填，再设为非空；任何无法唯一回填的记录都必须使迁移整体失败。迁移继续硬性限制
`current_database() = 'novelwriterdev'`，回滚只删除本迁移增加的表、列和组合唯一约束。

### 结构契约

schema contract 升级为版本 2，每张表必须采集、排序并比较 `CHECK` 约束名称、规范定义、是否验证和
`NO INHERIT` 状态。契约指纹必须覆盖这些字段。

生产关闭配置使用 `without_video_preview` 投影：同时从期望与实时结构移除六张 dev 视频表、
`ReviewArtifact.videoSceneId` 及其外键/索引、`ReviewArtifactKind.video_scene_plan`，以及仅为批准命令增加的
`Novel(id, userId)` 组合唯一约束。投影后重新计算指纹；它只允许生产安全关闭，不授权生产视频迁移。

### 运行时关闭

当 `VIDEO_PREVIEW_ENABLED=false` 时，Core 不得创建 `VideoRepository`、`VideoService` 或
`VideoTaskDispatcher`，视频公共接口统一返回服务不可用。生产配置必须拒绝开启 dev 视频预览。

### 真实数据库验收

新增显式 opt-in 的 PostgreSQL 集成测试。测试必须：

1. 二次确认实际连接数据库为 `novelwriterdev` 且目标不是回环地址；
2. 创建带唯一前缀的 User、Novel、WritingBible、VideoProject、VideoScene、完成任务和 ReviewArtifact；
3. 使用不同连接并发提交相同请求键和不同请求键，证明场景只加一次 revision、返回结果一致、命令键各自耐久；
4. 直接尝试写入跨场景命令，证明数据库组合外键拒绝；
5. 在 `finally` 中只按本次生成的精确 ID 删除测试根记录，并确认批准命令残留为零。

默认测试套件不得连接外部数据库；只有显式提供 `INKFORGE_VIDEO_DEV_DATABASE_URL` 时运行该测试。

### 部署脚本

## 视频域完整归属链加固

### 补充问题

1. `VideoScene.projectId` 与可选 `chapterId` 没有共同约束到同一本小说；
2. `ReviewArtifact.novelId` 与 `videoSceneId` 没有共同约束到同一本小说；
3. `VideoGenerationTask.projectId` 与 `sceneId` 可以分别指向不同项目；

`novelwriterdev`：

## 真实全流程回归后的架构修复

### 问题事实

真实 DeepSeek 全流程在第三阶段连续两次被摄影灯光草案的泛化 `anyOf` 拒绝。失败任务虽然已保存 canonical 故事
checkpoint，但用户显式重试会重新执行素材和故事阶段，重复消耗时间与积分。与此同时，本地 Core 只要开启视频预览
就会启动 dispatcher，并领取共享服务器 `novelwriterdev` 中任何开发者留下的到期任务；这会让一次普通本地启动改变
不属于当前开发实例的历史数据。前端还存在工作区固定最小宽度导致用户余额浮层覆盖模式按钮、编辑器字数与外壳摘要
不同步、视频生成使用固定两秒轮询等问题。开发启动入口依赖较新 Node API，且没有在拉起三个服务前统一检查版本和端口。

### 调度隔离

- `VIDEO_PREVIEW_ENABLED` 只控制页面和接口能力，不再隐式授权后台领取任务。
- `VIDEO_DISPATCH_ENABLED` 默认关闭；启用时必须同时提供符合小写字母、数字和短横线规则的稳定
  `VIDEO_DISPATCH_NAMESPACE`。生产环境固定拒绝启用。
- 新任务 jobId 带命名空间；dispatcher 只能领取当前命名空间前缀的任务，不能接管无命名空间历史任务或其他开发者任务。
- 本地统一启动脚本默认生成并注入当前工作副本的稳定命名空间；单独启动 Core 时没有显式开关就只提供 API，不运行视频
  后台任务。dispatcher 仍是耐久任务的唯一提交者，命名空间不是浏览器可控字段，也不改变用户/小说归属校验。

### 失败重试与计费补偿

- 失败重试按详细设计中的新规则复制最后一个已验证 canonical checkpoint；新任务只执行尚未完成的阶段，旧 reservation
  与原始模型草稿不复制。返工仍从头生成。
- 新视频模型 grant 的账本 requestId 必须带服务端生成的 taskId 作用域前缀。任务以业务失败收敛且没有生成
  ReviewArtifact 时，Core 在同一数据库事务中汇总该 taskId 的 `ai_charge`，恢复等额积分并写一条幂等
  `video_plan_refund` 账本；TokenUsage 仍保留真实供应商消耗。基础设施暂时错误、成功候选、用户批准后的正式内容均不退款。
- 旧式随机 requestId 无法无歧义归属到 taskId，因此不得猜测补偿历史账单；新规则只对升级后授权的调用生效。

### 前端与开发入口

- 工作区取消会把桌面画布强制撑出视口的固定 1440 像素最小宽度，余额浮层与模式导航必须保留独立命中区域；
  1280 像素桌面宽度下鼠标与键盘都能切换模式。
- 编辑器把当前草稿字数上报给工作区单一状态，章节列表、总字数、智能写作上下文和编辑器显示同一数值；保存失败时仍
  保留明确错误，不把未保存内容伪装成服务端已提交。
- 视频状态刷新改为可取消、无重叠的退避轮询：页面隐藏时暂停，生成中快速刷新，连续无变化后降低频率，终态立即停止。
  当前切片没有视频事件流端点，不用假 SSE 冒充推送；正式 SSE 作为独立公共契约变更。
- 根包声明受支持 Node 版本并提供 `.nvmrc`。统一启动脚本在导入版本相关 API 和拉起子进程前，从同一端口常量检查
  Web 43119、Core 8000 与 Agent 8001，发现占用时一次性给出清晰错误，不让三个服务部分启动。
- Core 与 Agent 的开发热重载只能监控各自 `src` 和共享契约/鉴权包；修改测试、文档或另一服务源码不得把两个 Python
  服务一起重启，避免无关文件变化中断在途任务。

### 真实供应商输出恢复

- Responses 的本地权威 Schema 仍负责拒绝非法结构；只有数学上完全等价的圆周方位角允许在校验前确定性归一到
  `-180..180`。该恢复必须同时覆盖 `video_cinematography_draft_v2.beatsByAlias` 下的摄影机、主光和可选边缘光，且不得
  改写高度、俯仰、滚转、曝光或其他非圆周事实。
- 第三阶段的正式自然协议仍以后续拍 `lightingCue=null` 表示灯光继承。为兼容供应商对旧协议的
  确定性镜像，本地复验前只允许把后续 B 拍中精确的 `"__INHERIT__"`，或
  `continuityMode="inherit"` 的灯光对象，归一为 JSON `null`。首拍、字符串 `"null"`、其他哨兵值和
  不完整的 `motivated_change` 对象仍必须由权威 Schema 拒绝；恢复不得改写任何实际灯光参数。
- 真实重试证明，某次响应可以先因灯光 `anyOf` 失败，纠错后才暴露 `lensType=zoom` 与非变焦运镜冲突；
  唯一纠错额度因而无法再修第二层错误。第三阶段 Responses Schema 必须用供应商支持的闭合 `anyOf`
  分支，在 wire 层绑定 `prime/macro_prime` 与非变焦运镜、`zoom` 与 `zoom_in/zoom_out`，并对变焦运镜
  锁定零位移和零旋转。起止焦距大小关系无法用当前窄 Schema 方言表达，仍由首调、固定自查和本地语义门禁共同保证。
- 同一问题也出现在拍内景别变化：三到四秒的短拍如果用 `continuous` 跨越过多景别，只在最终
  `ScenePromptSpec` 门禁才拒绝会浪费纠错机会。每个 B 拍的动态 Schema 必须使用服务器已知拍长收紧
  `shotProgression`：不到五秒的连续变化最多跨一级景别，五到不到六秒最多跨两级，更大变化必须显式选择
  `cut/match_cut/impact_cut`。首拍 `axisTransition` 同时直接锁定为 `hold`，不延迟到最终场景校验。
- 前移 Schema 能减少错误，但不能消除多层门禁的延迟暴露。真实重试中，素材也可能依次暴露额外字段、错用设定别名和背景人物等互不相同的问题。仍保持三次典型调用与五次耐久账本总上限，但两个额外纠正名额改为全流程共享：素材、故事或摄影都可以在当前阶段继续使用剩余额度；前序阶段多用一次，摄影就相应少一次，任何路径都不得出现第六次调用。
- `anyOf` 失败不得只返回 union 外层。诊断器必须在内存中对已知分支重放本地 Schema，选择与实例类型和字段形状最接近的分支，
  只返回最深的白名单 JSON Pointer 与 Schema keyword。原始字段值、未知字段名、分支错误正文和模型草稿仍不得进入结果或日志。
- 候选成功后的人工审核又暴露两类“结构合法、语义矛盾”：本场只出现关系的一端人物，却生成并强制引用了
  `relation_interaction` 素材；墙体破开后明写新的灯塔光束透入，该拍却使用 `lightingCue=null` 继承上一镜。
  素材阶段只有在关系两端人物都被原文逐字命中时才允许关系互动素材；只有一端、纯背景关系或本场不互动时必须拒绝。
  后续拍的故事动作、可见结果或摄影动机若包含白名单中的明确新光源透入、点亮、熄灭或遮挡事实，该拍不得使用继承，必须提交完整 `motivated_change`。
- 初态关键帧已通过 `anchorAssetAlias` 确定性锁定到最早机械起点。后续新道具首次出现不得再把所有初态关键帧重新塞入该拍；
- 初态关键帧门禁只认全场唯一的最早机械起点；仅当素材阶段确实声明了初态关键帧时，才可用最早道具入画拍作为无机械动作时的替代锚点。普通道具首次出现本身不得强制创建或重复引用初态关键帧；
  否则“铜扣插入齿槽瞬间”会在罗盘已显现的下一镜被错误重放。
- 共享 `ScenePromptSpec` 的最终门禁必须采用同一口径：唯一 `initial_state` 锚定全场第一个不可逆机关动作拍。该判定不能只信任模型选择的 `actionComplexity`；`mechanical_sequence` 直接命中，其他复杂度若动作文本同时含“插入/卡合/咬碎/弹开/启动/加速/提起/落下/砸碎”等状态变化和“机关/齿槽/齿轮/罗盘/牵引链/钟摆”等机械对象，也必须命中。只有全场完全没有这种动作时，才允许退回初态关键帧锚定道具的首次出现拍。中间穿插普通动作后再次出现机械动作不能被当作第二个初态起点。故事物化器、故事 checkpoint 复核与最终合并契约必须调用同一共享判定函数，避免已经通过的故事在摄影完成后才失败。
- 故事阶段必须把冻结原文中的每个可见事件放进所属拍的 `primaryAction` 或 `secondaryAction`；`dramaticPurpose`、表演、调度、摄影动机和声音只能补充意义与执行方式，不能代替可见动作，也不能把后拍事件提前写进前拍任务。原文明示人物对道具的情感价值时，应在该道具发生不可逆变化的当拍用克制、可见的即时反应体现，不得另造事后收尾。
- 故事阶段不能只靠提示词要求原文顺序，也不能继续在整段自由文本里按关键词首次出现位置推断顺序；“齿轮尚未加速”“钟摆落下前”等未发生状态会造成假阳性。服务器应把插入、咬碎、弹开、触碰、加速、提起、落下、砸碎等高信号机关事件归并为同义事件族，按冻结原文第一次出现位置生成连续的 `E01..ENN` 短别名与静态中文标签。真实调用已经证明 Responses v3 让模型自行填写 E 归属仍会反复产生 `E05` 被放到 `E08` 之后等自洽但错误的顺序，因此导演草案 1.4 必须改用故事 Responses v4：顶层 `beatsByAlias` 是服务器闭合的 B 对象，模型不再提交任何 E 字段；服务器在调用前把连续 E 事件按固定 B 拍均衡分组，并按当前拍可用的 `primaryAction -> secondaryAction` 槽生成唯一归属表，模型只填写这些槽的 `CameraActionUnit` 与拍级表演、调度、声音。物化时服务器把同一张归属表写入 story canonical checkpoint，再校验对应槽的 `subject/action/visibleResult` 是否以非否定、非“发生前”的方式落地事件。这样事件顺序由服务器结构决定，不再允许模型通过移动别名给错误动作“自证”；模型漏写或写错内容只产生精确的 `VIDEO_PLAN_SOURCE_EVENT_GROUNDING_INVALID`。冻结原文的事件提取词表与模型动作的语义落地词表必须分离：前者继续只用高精度原文触发词，后者可以接受“机关/齿槽挤压 + 铜扣碎裂或断成碎片”这类主体、动作、结果共同闭合的等价表达，但不能把没有机械施力语境的普通“断裂”误认成咬碎。v3 结构检查继续只用于读取既有 2.0 checkpoint 和诊断旧任务：同槽别名按冻结顺序解释，重复、缺失、倒置和不落地分别稳定拒绝；纠错只能附带服务器生成的 E 别名和静态事件族标签，不得回显原句、动作草稿、实体 ID 或自由文本。结构化归属随 story canonical checkpoint 持久化，摄影阶段不拥有也不能改写；缺少逐动作 E 归属的 1.0 story checkpoint 在升级到导演草案 1.4 时只能降级到已验证的素材 checkpoint 或从空阶段重跑，不能继续用自然语言猜测结果冒充同等证明。
- 冻结设定用于外观与世界连续性，不能替代本场原文新增剧情落点。场景元数据或动作若使用“露出/显现/出现”等揭示语句，揭示目标的核心名词必须能在冻结原文中找到；例如原文只写砸碎海侧墙时，不能凭设定背景补成“露出第七灯塔”。素材阶段和故事阶段均在后续模型调用前以 `VIDEO_PLAN_OFF_SOURCE_REVEAL` 拒绝，摄影阶段仍不得用灯光重新补回被上游拒绝的剧情对象。故事纠错必须只返回发生冲突的稳定 `Bxx.primaryAction/secondaryAction` 槽，不回显模型目标文本；若冻结原文在“砸碎/砸裂某物”处结束且没有继续揭示墙后对象，对应可见结果只能停在碎裂、碎片、裂缝或破口，不能把设定中的地点、灯塔、景物或光源续写到破口之后。摄影草案还必须逐拍证明 `cameraMotivation` 至少响应当前 B 拍服务器固定的一个 E 事件；把上一拍的咬碎反应写进弹匣/触碰拍，或把弹匣/触碰写进加速/提起拍，应一次聚合为 `VIDEO_PLAN_CAMERA_MOTIVATION_EVENT_MISMATCH`。`cameraSpec.focus.startTarget/endTarget` 不是机械参数，二者都必须属于当前拍的 E 事件对象或当前拍人物表演；若仍指向上一拍的铜扣碎片、罗盘或指尖，应按稳定 B 别名一次聚合为 `VIDEO_PLAN_CAMERA_FOCUS_EVENT_MISMATCH`。摄影动机、焦点目标、构图前后景、全局灯光或逐拍灯光若包含原文没有的灯塔等叙事对象，同次纠错以稳定 B 别名聚合拒绝，不得把目标原文回显给模型。摄影动机和灯光可以继续使用剧情揭示句门禁；焦点和构图是名词短语，只检查明确的原文外剧情对象，不能把“前景出现薄雾”等正常层次描述误判成新增剧情。
- `voice` 素材只表示人物声线、对白、呼吸、喊声等人物发声参考；金属卡合、碎裂、触碰、机关、脚步等同步拟音直接写入逐拍 `sound`，不能为了增加音频参考槽把拟音包装成 `voice`。素材语义门禁要求 `voice` 的目标或采用特征至少包含稳定人物发声标记，否则在故事调用前以 `VIDEO_PLAN_VOICE_ASSET_INVALID` 拒绝。
- “不创建 voice 参考素材”只约束素材职责，不能被改写成“禁止金属、机关、脚步、环境声等同步声音”。开发预览固定生成音频且每拍必须有环境声/拟音/对白，因此 `negativeConstraints` 中带否定语气并禁止环境声、同步拟音、机关声、金属卡合/碎裂、齿轮、钟摆、碰撞或摩擦声时，应在故事调用前以 `VIDEO_PLAN_REQUIRED_SYNC_SOUND_BANNED` 拒绝；禁 BGM、配乐、旁白或当前场景不需要的人物声线不属于该错误。
- `negativeConstraints` 同样不能把冻结原文明示的可见事件当成初态排除项扩散到全片。一个独立否定句同时命中冻结原文和禁项中的高信号动作（如插入、咬碎、弹开、触碰、加速、提起、落下、砸碎）时，素材阶段必须以 `VIDEO_PLAN_REQUIRED_VISUAL_EVENT_BANNED` 拒绝；只存在于 keyframe `excludeFeatures` 的“后续状态不参考”仍是该素材的局部约束，不能编译成全局禁止。
- 素材阶段“不生成表演或对白字段”只是阶段职责边界，不能扩散成全片“无角色表演”。当素材草案包含会进入逐拍引用的人物 identity、costume 或 voice 槽时，`negativeConstraints` 不得笼统禁止角色/人物的表演、动作、反应或表情；需要无对白时只能精确禁止对白。素材语义门禁应以 `VIDEO_PLAN_REQUIRED_PERFORMANCE_BANNED` 在故事调用前拒绝，1.3 共享 `ScenePromptSpec` 还必须按实际逐拍人物素材引用做最终兜底，防止旧检查点或其他入口把“每拍要求表演”和“全片禁止表演”同时交给 Provider。
- 素材阶段的纠错消息必须再次说明：返工中“不要创建某职责素材”的要求只通过省略对应槽位执行，不能把职责名、Schema 字段或流程说明复制/改写进 `negativeConstraints`。这条与来源二选一规则一起在每次素材重交时重复，避免强返工文本压过初始系统提示。
- 自动素材阶段不得创建 `camera` 参考素材。逐拍摄影与运镜由第三阶段的结构化 `cameraSpec` 唯一拥有，自动生成一段全局运镜参考会与不同镜头的锁机、推移、俯仰和切镜形成第二套事实；此类槽位以 `VIDEO_PLAN_CAMERA_ASSET_FORBIDDEN` 在故事调用前拒绝。未来若要支持用户上传的摄影参考，应由独立媒体绑定控制面显式引入，不能由模型凭空创建 fixture。
- 人物 `identity`、`costume`、`voice` 的 canon 槽只有在该人物姓名或别名被本场冻结原文逐字命中时才允许创建；唯一窄化例外是原文没有命中任何人名且冻结快照本身只有一名人物，此时“她/他”等代词可确定性落到唯一人物。设定快照中的其他背景人物不能因为与主角有关或模型想填满槽位而进入本场。素材 checkpoint 与 story checkpoint 都必须复核这一规则，并以 `VIDEO_PLAN_CHARACTER_ASSET_NOT_IN_SCENE` 拒绝，避免旧检查点绕过新门禁。
- 最终编译提示词超出 2000 字时，失败通常由素材描述、引用数量、故事动作和摄影共同造成，摄影阶段无权修改上游 canonical 内容。Core 在显式 retry 识别到稳定的 Provider 提示词超长错误后，不得继承 `scene_assets/story` checkpoint，应保留冻结输入但从 `empty` 重跑；其他摄影结构或语义错误仍可继承故事检查点。禁止通过截断、删尾或让摄影单独返工掩盖上游超预算。
- 若最终合并暴露 `VIDEO_PLAN_INITIAL_KEYFRAME_REQUIRED`，说明已有 story checkpoint 由旧版或不一致的初态锚点规则生成，不能继续只重跑摄影。Core 只有在该 story 中仍存在一份合法 `initial_state` 素材时，才可从 story 的场景与素材字段确定性重建 `scene_assets` checkpoint，并把重试降级到故事阶段；缺少初态素材或无法重建紧凑素材规范时必须从 `empty` 重跑。降级后的新任务只继承一次素材调用，不继承旧预留事件或错误故事内容。
- 1.3 的紧凑 Provider 投影必须始终保留每拍完整的 `performanceDirection`，不能只把它留在 Manifest，导致模型生成了人物即时反应而即梦实际收不到。第一档紧凑投影仍超出 2000 字时，第二档只能压缩重复的全片基线、摄影和灯光措辞，不能删除动作、表演、逐拍声音或截取半句；第二档仍超限必须稳定失败并要求上游重规划，禁止以“表演只留 Manifest”的降级伪装成功。Provider 全局声音句和服务器追加的 canonical 禁 BGM 约束都只能收束为“各镜头明确写出的声音”，不能额外放宽为对白、旁白或其他未在逐拍声明的声音，避免 Provider 与 Manifest 任一层出现“禁止对白但同时允许对白”。
- 摄影 Responses Schema 的首拍和变化拍灯光分支必须在供应商侧拒绝空的 `motivatedChange`；提示词与纠正清单同时要求首拍写明建立灯光的画内来源、变化拍写明可见触发事件，避免把可预防的空字符串错误拖到本地预算末端。
- 首拍和变化拍的完整灯光对象继续按补光策略拆成闭合分支：`fillStrategy=none` 时 `fillRelativeStops` 只能为 `-8`，其余策略不能选择 `none`。关闭值是协议机械事实，不得让模型在本地根校验中反复猜测。
- `fillDirection` 在正式灯光契约中改为可空：无补光时必须使用自然 `null` 且编译为“无补光”，有补光时必须填写真实方向。旧 strict wire 若在无补光时携带占位方向，归一化器忽略该无意义值并收敛为 `null`；不得再编译出“无补光从某方向作用”的矛盾语句。
- Responses 兼容恢复以 `fillStrategy` 作为补光开关的唯一权威事实。v2 灯光对象选择 `none` 时，`fillDirection` 与 `fillRelativeStops` 都不再承载创意：只要前者是字符串或自然 `null`、后者是合法范围内的有限数值，服务器就确定性收敛为 JSON `null` 与 `-8`，并记录 `normalize_cinematography_no_fill_direction`；容器、布尔值、非数值、越界数值、协议版本或拍点形状不匹配时仍拒绝。启用补光时，供应商若只把相邻 `negativeFillSide` 坐标词 `camera_left`/`camera_right` 误用于 `fillDirection`，兼容层可分别投影为 canonical 的 `side_left`/`side_right` 并记录 `normalize_cinematography_fill_direction_alias`；`none`、`both`、自由文本及其他未知值不得猜测。正式契约与 Provider 编译始终只读取 canonical 方向，避免两套方向词继续向下游扩散。
- 短拍景别跨度已经由固定时段和起止景别决定，不再为一个机械可行性错误反复消耗摄影纠正预算。v2 草案若把唯一一个 Schema 判定为不可执行的 `continuous` 改成中性的 `cut` 后整份草案恰好通过，而原稿不通过，则供应商恢复层可只改该 `changeMode` 并记录 `normalize_cinematography_infeasible_continuous_cut`。起止景别不变，不猜 `match_cut` 或 `impact_cut`；零个或多个候选能通过、原值不是 `continuous`、协议版本不符时都必须拒绝恢复。
- 摄影 wire 中 `travelDistanceMeters`、`rotationDegrees` 的方向已经由 `movementType` 表达，`keyToFillStops` 也是主补光档差的大小；三者都是无符号量。v2 供应商若只多写了负号且绝对值仍在各自合法上限内，恢复层可确定性取绝对值并记录 `normalize_cinematography_unsigned_magnitudes`。不得触碰方位角、曝光补偿等有符号量，也不得夹取越界值、布尔值或非数值。
- 自动摄影草案的 `axisSide` 使用统一 wire 坐标约定：只允许 `screen_left` 或正轴 `on_axis`，从 Schema 层保证所有非正轴镜头同侧；具体机位方位仍由有符号 `azimuthDegrees` 表达。共享正式契约继续保留左右轴线与有意越轴能力，自动规划路由不得靠提示词让模型重复维护一份易漂移的左右标签。
- 因自动 wire 已采用单侧坐标约定，当前 `video_cinematography_draft_v2` 同时固定 `axisRule=maintain_180` 且每拍 `axisTransition=hold`；有意越轴和无轴线场景继续保留在共享正式契约，待独立导演控制面提供可审核的重置镜头后再开放给自动路由。不能让模型选择当前 wire 无法实际执行的越轴模式后，在最终根校验耗尽调用预算。
- 故事草案的 `primaryAction`/`secondaryAction` 在 wire 中表示“先发生/后发生”，不是“重要/次要”；跨拍和同拍动作都必须保持冻结原文顺序。素材阶段的 `negativeConstraints` 只允许最终供应商需要执行的画面或声音禁项，返工流程说明、A/B/R 别名、镜头编号、Schema 字段名、职责枚举和 `motivated_change` 等内部协议词必须在故事调用前拒绝，不能泄漏进 Provider 提示词。
- `initial_state` 素材只能描述首个不可逆机械动作发生前或临界起点的画面；未带“未/尚未/即将/将要/准备/等待/尚待”前置限定或“前/之前”后置限定的触碰后、弹开、露出、加速、碎裂、坠落和破墙状态必须在故事调用前拒绝，防止“触碰罗盘瞬间初态”被确定性锚定到更早的插扣镜头。限定词只在后续状态词的近邻范围内生效，不能让句子远处一个无关的“未”掩盖真正的结果态。
- 场景素材 Responses 偶尔会回显由服务器独占派生的 `settingId`、`bindingScope`、`modality`、`keyframeRole`、`assetId` 或逐拍使用位图。这些字段不承载模型创意，解析层可以在本地 Schema 复验前按静态白名单整字段丢弃，随后仍由服务器从 `sourceAlias`、`duty` 与后续故事阶段确定性派生；不在白名单中的未知字段必须继续按 `additionalProperties` 拒绝，不能演变成通用的宽松 JSON 清洗。
- 第一阶段 Responses Schema 必须直接绑定冻结设定别名与允许职责：`C` 只允许人物身份/服装/声线，`R` 只允许关系互动，`L` 只允许场景，`I` 只允许道具，`W` 只允许视觉风格；本场临时目标仍允许按职责直绑。纠错消息重复这一静态映射，不能等到物化阶段才用 `VIDEO_DRAFT_SOURCE_DUTY_MISMATCH` 告诉模型，也不能把错误地点别名静默猜成道具别名。
- 素材语义门禁拒绝未在本场原文出现的背景人物时，纠错必须带上该人物在同一请求里已经公开给模型的稳定 `Cxx` 短别名，明确要求移除其 `identity/costume/voice` 槽；不得回显人物原名、数据库 ID、正式素材 ID 或原始草稿值。只返回泛化的“存在背景人物”会让模型无法定位并重复消耗全部纠正预算。
- 同一条作者返工意见会随冻结任务进入三阶段，但每个阶段只能处理自己拥有的部分：素材阶段只处理场景、素材、初态、风格与最终禁项，忽略故事动作、表演、声音、摄影灯光和 Provider 编译；故事阶段只处理节拍、动作、表演、调度、素材使用与声音，忽略素材重建、摄影灯光和 Provider 编译；摄影阶段只处理摄影、灯光与转场，忽略上游 canonical 与 Provider 编译。每阶段用户消息标题和系统提示都必须明示该边界，避免技术性返工文字污染无关阶段。
- 返工任务不能只冻结一句 `revisionInstruction` 后从空白重新抽签。Core 必须把当前待审 `scenePlan` 作为通过共享契约校验的 `revisionBaseline` 一并冻结；Agent 只向三个阶段投影各自拥有的上一版创意事实，并移除正式素材 ID、数据库 ID 和内部节拍 ID。模型应保留返工未要求改变且不与原文冲突的事实，冻结原文和新返工意见优先于旧候选。这样“保持现有摄影设计不变”至少有真实上一版可参照，且重试、幂等和输入指纹都绑定同一基线，不能把审计快照当作仅供数据库留档的死数据。但“曾经通过旧契约”不等于“永远可信”：每个阶段投影前必须用当前冻结原文和当前门禁重新筛选旧候选。素材元数据含原文外揭示时整段素材基线不再提供给模型；故事动作含原文外对象、事件缺失或事件倒序时整段故事基线不再提供，不能让旧的“第七灯塔”和错误 `E05` 顺序反复污染 v4。摄影基线必须继续拆分所有权：焦距、T 值、数值机位、构图规则、主体占比、运镜、景深、拉焦方式和时长可以作为机械设计保留；`focus.startTarget/endTarget`、构图前后景、摄影动机和灯光文字仍是故事语义。旧故事整体不兼容时必须从摄影基线省略这些语义字段；故事兼容但焦点目标不属于对应当前拍时，也必须成对省略起止目标，让模型保留机械设计后重新填写，不得把错拍焦点继续当成“保持摄影设计”。含原文外揭示的摄影语义同样按字段省略。筛选只能影响本次只读上下文，不能改写审计快照。
- JSON Schema 无法表达的摄影跨字段门禁仍由共享 `ScenePromptSpec` 裁决。一次纠错消息只能返回服务端静态白名单中的
  规则说明，不能携带模型原始草稿、字段值、正式素材 ID 或未知字段名；已知规则不得退化成无意义的
  `root: code=value_error`。
- 开发预览开启时，尚未加入静态白名单的 Pydantic 自定义错误可以只在服务端告警日志记录校验器生成的 `loc` 与 `msg`，并继续向模型和浏览器返回脱敏结果；必须使用 `include_input=False`、`include_context=False`，不得记录原始输入、模型草稿或异常上下文。该日志只用于补齐稳定错误映射，不能成为正式纠错协议。
- 第三阶段系统提示必须明示拍长相关的拉焦、位移、景别变化和轴线约束，使首调与本地语义门禁一致；提示不是放宽
  正式契约的依据。
- Pydantic 跨字段校验产生的 `value_error` 必须覆盖摄影、焦点、镜头、轴线和灯光职责的静态规则白名单；尤其是
  首拍灯光建立、主光/边缘光职责和关闭补光值，不能只返回没有修复方向的 `root` 或拍点路径。纠错仍不得回显
  草稿值、正式 ID 或未知字段。
- 第三阶段一次响应可能先被缺字段挡住，完整重交后才暴露轴线或灯光跨字段冲突。因此唯一一次纠错除了当前精确规则，
  还必须附带固定、短小的提交前自查：每个 B 拍点字段完整、`maintain_180` 非正轴镜头同侧、主光/边缘光职责合法、
  继承灯光只能用后续拍的 JSON `null`，不能输出字符串 `"null"`、`"__INHERIT__"` 或
  `continuityMode="inherit"` 对象。该清单是静态规则，不增加模型调用，也不能包含本次草稿值。

### Provider 紧凑投影

真实四拍规划证明，完整 1.3 导演语义直接拼接后可能达到 3000 字以上，即使每个独立字段都满足 Schema 上限，仍会
被 2000 字产品安全包络拒绝。这里不能放宽包络或按字符裁切，也不能让完整 Manifest 的长度阻断 Provider 文本。

- 编译器先生成完整自然导演投影；仅当 1.3 投影超过 2000 字时，才确定性切换到紧凑投影。紧凑投影必须保留每一拍、
  每一个动作单元、该拍素材别名、可见摄影结果、动机光结果、同步声音与转场，不能删除时间段或动作。
- 戏剧任务、表演细节、调度、摄影动机、工程参数及全场长说明仍逐字保留在结构化 `ScenePromptSpec` 和
  `manifestPrompt`。紧凑层只去掉与上述可见事实重复的自由文本，不做子串截断，并在 `warnings` 中明确标记采用了
  紧凑投影，避免把信息降级伪装成完整 Provider 稿。
- 紧凑投影后仍超过 2000 字时继续明确编译失败；不得继续删动作、只留首尾拍或通过提高上限掩盖异常膨胀。

### 验收补充

- 两个 dispatcher 使用同一数据库但不同命名空间时只能领取各自任务；默认关闭时零领取，历史无命名空间任务不变化。
- 摄影 Schema 对首拍和后续拍生成不同闭合约束；首拍 null 在发起下一次业务阶段前即可得到稳定、精确诊断。
- 后续拍的旧继承哨兵和 `continuityMode="inherit"` 对象可在不改写输入容器的前提下恢复为 `null`；
  首拍与不合法的变光对象仍被拒绝，并留下不含原始草稿的恢复审计代码。
- 供应商 wire Schema 能在本地 Pydantic 物化前拒绝 zoom 镜头配非 zoom 运镜、定焦镜头配 zoom 运镜，
  以及 zoom 运镜带位移或旋转；原始 Schema 与 DeepSeek 窄方言投影均保留这些分支。
- 三、四秒短拍的连续景别跨度和首拍 `axisTransition=hold` 在 Responses Schema 层即可验证；大跨度改为明确切镜后仍可通过。
- 从 `story` checkpoint 开始且前序未消耗纠正时，摄影最多可预留三次调用（首调加两次纠正）；第五次后稳定拒绝，崩溃恢复不重复计数。
- 嵌套 `anyOf` 失败能安全收窄到已知内层字段；含私密值或未知字段的夹具证明这些内容不出现在诊断、应用结果或日志。
- 原文只命中关系一端时，关系素材在故事调用前即被稳定拒绝；两端均命中时仍可使用。
- 明确“灯塔光束透入”的后续拍使用 `null` 会进入摄影纠正，改为完整 `motivated_change` 后通过；不含光变事实的后续拍仍可继承。
- 初态关键帧只出现在锁定起点；后续新道具首次出现不会导致该关键帧被重复引用。
- 从 `story` checkpoint 重试时只发生摄影阶段调用，最多再纠正一次；返工仍发生完整三阶段调用。
- 失败回调与重复回调只产生一条退款账本，积分恢复但 TokenUsage 不删除；成功任务不退款。
- 四拍长导演语义能在不截断动作的前提下编译为不超过 2000 字的紧凑 Provider 稿；Manifest 仍包含被紧凑层省去的
  全部自由导演字段，异常长动作本身仍会明确失败。
- 1280 像素浏览器回归、编辑后字数同步、退避轮询、Node 版本及端口预检均有自动化测试。
