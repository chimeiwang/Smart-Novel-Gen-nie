## 问题与目标

9 月 29 日生产章节任务在 `get_outline_node` 参数预检中连续失败。模型可见 Schema 将两个定位字段
都设为可选，而本地要求至少一个；纠正只有根级 `value_error`，未说明定位约束。同类跨字段规则也存在于
产物、项目定位和复审工具。生产 Core 后台异常日志缺少实际可见的任务身份及安全异常栈；无效
`Next-Action` 请求进入没有 Server Action 的 Web，产生重复异常。

目标是提高参数生成、有限纠正及诊断的可靠性，保持产品业务规则、权限、计费、作者确认和持久结果契约。

## 工具契约

1. 大纲、项目和草案定位的“至少一个非空字符串”规则进入模型 Schema，并保留原有可接受组合与本地
   复验；`required` 分支必须同时约束值类型，不能让 `null` 仅因键存在而通过。不新增业务语义门禁。
2. 普通产物和选区产物按当前 Operation 选择模型可见 Schema；普通正文要求完整 `content`，选区要求
   完整冻结身份及 `replacement`，两者互斥。本地完整参数校验及 Core 身份校验继续保留。
   预检先沿用原契约归一化，显式可选 `null` 仍等价于省略；操作范围检查使用归一化后的执行参数，
   不能让模型 Schema 收窄把历史等价输入升级为业务错误。
3. 复审结论的 `verdict/revisionMode/patches` 组合进入 Schema；不可直接表达的区间等语义约束使用
   稳定错误码和固定安全纠正指令。保留原有 pass/block/patch/rewrite 的产品语义。
4. 新模型输入不请求 `beatCount`，在工具预检边界按已校验的 `sceneBeats` 确定性派生。提交事件及 Core
   接收仍保留整数 `beatCount`；历史事件和旧参数模型继续可按既有契约读取，不静默修正显式矛盾的旧值。
5. 模型输入模型、执行参数和历史持久结果按职责区分；不得替换已注册 `ToolDefinition` 对象绕开身份校验。

## 纠正与日志

- 根级参数错误提供稳定分类；运行时只将白名单固定说明与现有脱敏字段路径反馈给模型，不回放坏参数、
  原始异常消息或模型推理。大纲定位提示可指引先读真实索引，不允许猜测节点。
- Core 监督器输出任务名、错误分类、异常类型、连续失败数和退避时间，并记录稳定恢复事件。
- 真实控制台格式须显示附加字段。安全异常诊断只保留类名、栈帧、因果关系等允许信息；不写异常 message、
  SQL、参数值、凭据或原始 URL。正常提前返回与异常结束可区分；不静默截断诊断。
- 保留现有监督器退避、稳定窗口和 readiness 行为。本次日志整改不能证明此前未知异常的根因已修复。

## Web 边界

在 Compose Nginx 的 Web `location /` 拒绝非空 `Next-Action` 请求头，返回 404。规则不进入更优先的
Core `/api/v1/` 和 `/api/v1/video/` location；普通页面、静态资源、API POST、SSE 与上传代理规则保持。
今后若产品新增 Server Action，必须同时重新评估此边界。
