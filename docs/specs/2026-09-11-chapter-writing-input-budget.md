# 正文写作输入预算调整

后续新 Run 额度由 [各项 token 预算统一](2026-09-11-chapter-writing-token-budgets.md) 取代；本文保留 v1/v2 历史变更依据。

日期：2026-09-11。状态：代码调整及本地相关回归完成，未部署。用户已明确要求先修改代码，
将本次正文写作的 30,000 输入限制调整为 100,000。

## 原因与范围

生产第 18 章正文生成在调用模型前失败。按冻结数据重建，完整输入计数为 41,862，超过原单步
30,000 上限；其中包含完整大纲、相关设定及来源绑定记录。当前执行器使用字符数估算输入，
本次只调整预算，不改变估算算法、上下文内容或异常分类。

## 调整设计

- `long_serial.write_chapter` 的正文生成、校验复审和编辑复审分别新增 v2 Step Budget，
  `maxInputTokens` 与 `maxPromptCacheMissTokens` 均为 100,000。
- 新写作 Run 使用 v2 Run Budget，两项累计输入上限由 180,000 调整为 600,000，继续覆盖最多六次模型调用，
  避免新增的单步额度无法通过生成与双复审的整轮预算预检。
- 旧 v1 Step Budget 保留原值，已有 Run 的冻结快照不改写。场景改写等其他操作继续引用原预算，
  不因共享 Reviewer 而扩大其额度。
- 旧 Run 的后续复审或作者返工也可能是首次派发；Agent 对正文写作的三份新预算显式保留对应 v1 的
  精确匹配，避免只兼容重派而拒绝旧 Run 后续步骤。不接受其他操作或任意自定义预算。
- 模型调用次数、输出、推理、费用、墙钟和重试上限保持原值；完整内容仍不得截断。
- 同步执行资产 manifest 哈希；不变更公共接口、数据库结构、生产配置，不在本次部署或重试生产任务。
  执行资产 JSON 固定 LF 换行，避免 Windows 自动换行使字节哈希与发布环境不一致。

## 验收

- 约 40,000 字符的完整章节上下文能够构造正文生成与两类复审请求，超过新上限时继续明确拒绝。
- 旧 30,000 冻结预算的恢复路径仍可识别，其他操作原有预算不变。
- Python 与 Java 均能加载更新后的执行资产，预算与 manifest 校验通过；运行相关回归、Ruff、Mypy
  及 `git diff --check`，记录真实结果。
