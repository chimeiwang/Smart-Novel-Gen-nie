# 中短篇双文档选区修改与版本工作流规格

## 状态

- 日期：2026-07-30
- 状态：设计方向已确认，规格待用户复核
- 实施基线：`codex/short-medium-writers-room` 分支的 `942d734`
- 数据库：禁止修改 PostgreSQL schema
- 范围：6000～80000 字中短篇的创建、可编辑大纲、完整正文、选区 AI 修改、显式版本、恢复和 Diff

## 背景

当前产品虽然已经存在 `short_medium` 篇幅 Profile，但创作流程、篇幅配置、剧情结构和正文生成仍以长篇章节为中心。用户需要在长篇小说生成之外，使用一段灵感、一个开头、一个结尾或一份简略大纲开始创作 6000～80000 字的中短篇小说。

中短篇第一期的重点不是建立自动维护全部因果关系的复杂系统，而是：

- 让用户能够直接编辑大纲和正文；
- 让 Agent 只修改用户明确选中的区域；
- 让每次 Agent 任务产出形成可追溯的候选版本；
- 让人工编辑只有在用户显式提交后才形成版本；
- 让正文生成固定绑定明确的大纲版本；
- 让用户能够查看版本差异、采用候选版本和恢复历史版本。

本规格不复用本机 `main` 分支上已经证明失败的中短篇专用实现。实现必须从本规格指定的当前基线重新开始，只复用当前基线已有的数据库结构、公共服务边界、写作任务、ReviewArtifact、SSE、幂等命令和前端基础组件。

## 当前项目事实

### 篇幅与创建

- `WritingBible.storyLengthProfile` 已支持 `short_medium` 和 `long_serial`。
- `WritingBible.targetTotalWordCount` 是可空整数，数据库没有 6000～80000 的上下界约束。
- 当前 `CreateNovelRequest` 已包含 `storyLengthProfile`、`targetTotalWordCount` 和 `summary`，但没有起始素材类型。
- 当前前端把 `short_medium` 配置为 30000～100000 字、8～25 章、3～5 个剧情单元，与本规格目标不一致。
- 当前中短篇未填写目标字数时默认使用 80000，不适合作为第一期默认体验。
- 当前新建作品统一创建“第一章”、空文本大纲和 WritingBible。

### 写作与提示词

- 当前剧情 Agent 仍以阶段、剧情单元和章节组组织大纲。
- 当前写作 Agent 依赖章节目标、已批准 Beat Plan 和章节组映射。
- 当前 CreativeOperation 只有长篇语义下的创建/修改大纲、规划章节、写章节和改写场景等操作。
- Agent ID 固定为设定、剧情、写作、校验和编辑；本功能不需要新增“短篇 Agent”。
- Agent 消息已经按静态 system prompt、执行 brief、只读上下文、历史消息和唯一当前用户消息构造。中短篇不得通过重复注入完整聊天历史解决上下文问题。

### 正式内容与版本基础

- 用户手动修改章节正文可以直接保存。
- Agent 对正式大纲和正文的变更必须先形成 ReviewArtifact，并由用户确认后才能应用。
- `ReviewArtifact` 已包含 `artifactKey`、`kind`、`status`、`payloadJson`、`diffJson`、`revision`、`createdByAgent`、`updatedByAgent` 和 `appliedAt`。
- `ReviewArtifactKind` 已包含 `outline_draft`、`chapter_draft` 和 `chapter_content`，本功能不新增数据库枚举。
- `ReviewArtifactRevision` 已保存完整 `payloadJson`、`diffJson`、revision、summary 和可空的 `createdByAgent`。
- 当前公开接口只能读取单个 ReviewArtifact、读取任务绑定的 Artifact 和提交草案决定；尚未提供文档级版本列表、人工提交版本、任意版本 Diff 和恢复接口。
- 当前 Agent 内部创建 Artifact 时要求非空 `createdByAgent`；人工版本必须走新的 Core 公共版本服务，不能伪装成 Agent 版本。

### 工作稿保存

- 当前章节编辑器使用 `textarea`。
- 当前章节编辑器使用 1.2 秒自动保存、`expectedUpdatedAt` 并发控制和浏览器本地草稿恢复。
- 当前已经存在 `PUT /api/v1/novels/{novelId}/outline`，但请求只有 `content`，尚未提供与章节编辑等价的 `expectedUpdatedAt` 并发校验和 `contentHash` 响应。

## 目标

- 将中短篇支持范围明确改为 6000～80000 字。
- 用户可以使用灵感、开头、结尾、简略大纲或混合素材创建中短篇。
- 用户只面对“故事蓝图”和“完整正文”两个核心文档。
- 故事蓝图和正文都可以直接手动编辑并自动保存为工作稿。
- 自动保存只保护工作稿，不自动创建版本。
- 用户点击“提交大纲版本”或“提交正文版本”并确认后，才创建人工版本。
- Agent 每完成一次会改变大纲或正文的任务，就创建一个不可变候选版本。
- Agent 候选版本必须由用户点击采用后才成为当前版本。
- 对已有大纲或正文执行 AI 修改时，Agent 只修改用户选择的区域；选区之外必须逐字保持不变。生成蓝图、首次生成正文和用户显式点击“重新生成正文”属于独立的完整文档任务。
- 用户能够比较任意两个版本、采用候选版本并恢复历史版本。
- 正文生成只读取最新已提交并采用的大纲版本。
- 每个正文版本必须记录其来源大纲版本。
- 长篇连载现有章节、Beat Plan、逐章写作和审核行为保持不变。
- 不修改 PostgreSQL schema。

## 非目标

- 不建立自动维护人物、因果、时间线和设定的连续性账本。
- 不建立通用叙事图、稳定场景 ID 系统或自动下游影响传播。
- 不允许 Agent 根据一个局部修改要求自动改动未选中的其他区域。
- 不做多个 Agent 自动讨论、投票、审核或返工的作家室。
- 不让编辑或校验 Agent 自动改稿。
- 不把中短篇拆成数据库中的多章、多节任务或多个正式正文容器。
- 不为每次按键、自动保存或光标移动创建版本。
- 不把内部正文分段生成的每次模型调用记录成用户版本。
- 不新增 ShortStory、StoryVersion、DraftSession 等 PostgreSQL 表。
- 不新增或修改 PostgreSQL 枚举。
- 不提供 `short_medium` 与 `long_serial` 的自动双向迁移。
- 不实现多人实时协作编辑。

## 核心术语

### 工作稿

工作稿是当前编辑器中的可编辑内容：

- 用户输入后按 1.2 秒自动保存；
- 刷新或异常离开后可以恢复；
- 可以与最近当前版本不同；
- 不出现在版本历史中；
- 不允许作为正文生成或 Agent 修改的隐式权威输入，除非先提交为版本。

编辑器必须明确显示以下状态之一：

- 已与当前版本一致；
- 有未提交修改；
- 正在保存工作稿；
- 工作稿保存失败；
- 工作稿与服务端版本冲突。

### 候选版本

候选版本由会改变大纲或正文的 Agent 任务产生：

- Agent 任务成功完成后自动创建；
- 立即进入版本历史；
- 默认不写入当前工作稿；
- 默认不成为当前版本；
- 用户可以查看内容和 Diff；
- 用户可以采用，或者暂不采用并让它留在版本历史中。

Agent 任务失败、输出截断、内容过滤、缺少完整边界或回调未完成时不得创建候选版本。

### 当前版本

当前版本是当前文档最后一次被用户明确确认的不可变快照。它可以通过以下操作产生：

- 用户提交人工工作稿；
- 用户采用 Agent 候选版本；
- 用户确认恢复历史版本。

同一文档同时只有一个当前版本。旧版本不删除，只在显示上失去“当前”标记。

### 版本序列

大纲和正文拥有互相独立的版本序列：

- 大纲使用“大纲 v1、v2、v3……”；
- 正文使用“正文 v1、v2、v3……”；
- 候选版本也占用版本号；
- 未采用版本继续保留原版本号；
- 幂等重试不能创建第二个版本或消耗新的版本号；
- 版本号只增不减，不因恢复历史版本而回退。

## 设计方案

### 1. 用户可见主流程

~~~mermaid
flowchart TD
    A["输入灵感、开头、结尾、简纲或混合素材"] --> B["创建中短篇项目"]
    B --> C["生成或编辑故事蓝图工作稿"]
    C --> D{"如何形成蓝图版本"}
    D -->|"人工编辑后提交"| E["人工大纲版本"]
    D -->|"Agent 任务完成"| F["Agent 大纲候选版本"]
    F --> G{"用户决定"}
    G -->|"采用"| H["当前大纲版本"]
    G -->|"暂不采用"| C
    E --> H
    H --> I["生成完整正文"]
    I --> J["Agent 正文候选版本"]
    J --> K{"用户决定"}
    K -->|"采用"| L["当前正文版本"]
    K -->|"暂不采用"| P["候选留在版本历史"]
    L --> M["正文工作稿"]
    M --> N["提交正文版本"]
    N --> L
    L --> O["手动编辑或选区 AI 修改"]
    O --> M
    O --> J
~~~

用户界面只需要：

- “蓝图”和“正文”两个页签；
- 当前文档的 `textarea`；
- “提交大纲版本”或“提交正文版本”按钮；
- “AI 修改选中内容”按钮；
- “版本”入口；
- 尚无当前大纲版本时出现的“生成蓝图”按钮；
- 大纲确认后出现的“生成正文”按钮；
- 可选的“全文检查”按钮。

### 2. 创建入口与起始素材

中短篇创建表单只保留：

- 标题；
- 目标总字数；
- 起始素材类型；
- 起始素材正文；
- 可选题材。

起始素材类型：

- `idea`：灵感；
- `opening`：开头；
- `ending`：结尾；
- `outline`：简略大纲；
- `mixed`：混合素材。

创建规则：

- `storyLengthProfile` 必须为 `short_medium`。
- `targetTotalWordCount` 必须为 6000～80000。
- 起始素材正文必须非空，禁止静默截断。
- `Novel.summary` 兼容保存用户起始素材原文。
- `WritingBible.notes` 使用稳定文本信封保存 `sourceKind` 和完整 `sourceText`，作为起始素材的权威备份，禁止静默截断。
- 第一份大纲版本 payload 同时保存 `sourceKind` 和完整 `sourceText`，用于追溯蓝图来源。
- `opening` 同时初始化唯一“全文” Chapter 的工作稿内容。
- `outline` 同时初始化 Outline 工作稿内容。
- `ending` 只作为起始素材保存，不能错误写入正文开头。
- 中短篇唯一 Chapter 标题为“全文”。
- 未创建任何大纲版本时，初始化内容只属于工作稿。

前端提供常用目标字数快捷值：

- 8000；
- 20000；
- 40000；
- 80000；
- 自定义 6000～80000。

第一期不提供空目标或“智能决定篇幅”，避免模型在创建后自行扩大故事规模。

### 3. 可编辑双文档

#### 3.1 故事蓝图

故事蓝图是自由文本，不使用阶段、剧情单元、章节组或 Beat Plan 的强制结构。推荐但不强制包含：

- 故事核心；
- 主要人物；
- 开端承诺；
- 关键冲突；
- 重要转折；
- 高潮选择；
- 结局兑现；
- 自然段落或分节安排。

用户可以：

- 直接编辑全部蓝图；
- 选择一段让 Agent 修改；
- 提交当前工作稿为人工大纲版本；
- 查看、采用、比较和恢复历史大纲版本。

Outline 需要扩展现有公开保存能力，并使用与章节保存一致的：

- 1.2 秒自动保存；
- `expectedUpdatedAt`；
- 同一文档串行保存；
- 版本冲突提示；
- 浏览器本地工作稿恢复。

#### 3.2 完整正文

中短篇只使用一个标题为“全文”的 Chapter：

- 正文可以包含用户自己编写的自然分节或短章标题；
- 自然分节不创建数据库 Chapter；
- 用户可以直接编辑全部正文；
- 用户可以选择一段让 Agent 修改；
- 用户可以提交当前工作稿为人工正文版本；
- 用户可以查看、采用、比较和恢复历史正文版本。

现有章节 `textarea`、字数统计、1.2 秒自动保存和并发控制继续复用。

### 4. 版本数据模型

#### 4.1 不新增数据库表

文档版本是基于现有 ReviewArtifact 的应用层视图：

- 大纲版本使用 `kind=outline_draft`；
- 正文版本使用 `kind=chapter_draft`；
- Agent 候选版本使用 `status=awaiting_user`；
- 已提交人工版本和已采用 Agent 版本使用 `status=applied`；
- 人工版本的 `createdByAgent` 和 `updatedByAgent` 为 `null`；
- Agent 版本保留真实 Agent ID；
- `artifactKey` 用于组织文档版本序列；
- `payloadJson` 保存完整不可变版本内容和版本元数据；
- `diffJson` 保存相对基础版本的默认 Diff；
- `ReviewArtifactRevision` 保留该 Artifact 自身的完整修订快照，不直接充当跨任务的文档版本号。

版本的 `content`、`contentHash`、`versionNumber` 和来源字段一经创建不可修改。候选版本被采用时只允许推进 `status`、`appliedAt` 等生命周期字段，不得改写版本内容。

稳定 `artifactKey`：

```text
short-medium:outline:{novelId}
short-medium:manuscript:{chapterId}
```

同一 `artifactKey` 可以有多个 ReviewArtifact。版本列表按 `artifactKey` 聚合，而不是把所有历史压进一个永远不终止的 ReviewArtifact。

`short-medium:outline:` 和 `short-medium:manuscript:` 前缀由文档版本服务独占：

- Agent 完成回调必须进入文档版本服务，不能调用通用 `create_or_revise` 改写既有版本；
- 通用 ReviewArtifact 的 `approve`、`revise` 和 `discard` 接口遇到这两个前缀必须拒绝并引导到文档版本接口；
- 文档版本不允许使用通用 `discard` 物理删除；
- 采用候选版本时，Core 必须在同一数据库事务中锁定候选 Artifact 和 Outline/Chapter，完成工作文档写入、候选状态推进及 `appliedAt` 更新。

#### 4.2 版本载荷

每个版本 payload 至少包含：

```text
kind
documentType: outline | manuscript
versionNumber
baseVersionId
clientRequestId
source: agent | manual | restore
content
contentHash
sourceTaskId
sourceOutlineVersionId
userInstruction
sourceKind
sourceText
restoredFromVersionId
createdFromSelection
selectionStart
selectionEnd
selectedTextHash
```

字段规则：

- `sourceTaskId` 只在 Agent 版本中必填。
- `clientRequestId` 在人工提交和恢复产生的新版本中必填；Agent 候选版本按 `taskId/jobId` 去重。
- `sourceOutlineVersionId` 在所有正文版本中必填。
- `userInstruction` 保存 Agent 任务的用户原话；人工提交可以为空。
- `sourceKind` 和 `sourceText` 只在需要追溯起始素材的首个大纲版本中填写。
- `restoredFromVersionId` 只在恢复产生的新版本中填写。
- 只有选区 Agent 修改才填写 selection 字段。
- `contentHash` 使用完整内容的 SHA-256。
- `baseVersionId` 指向本版本直接基于的版本；首个版本为 `null`。

#### 4.3 版本号分配

Core 在创建版本时：

1. 大纲版本先锁定 Novel；正文版本先锁定 Chapter。
2. 按目标 `artifactKey` 读取现有版本数量和最大版本号。
3. 分配下一个单调递增版本号。
4. 在同一事务中创建 ReviewArtifact 和初始 ReviewArtifactRevision。
5. 人工提交和恢复在文档锁内按 `clientRequestId` 查询，命中时返回原版本；Agent 完成回调按同一 `taskId/jobId` 返回原候选版本。

人工提交、Agent 完成回调和恢复操作必须调用同一个 Core 版本服务。Agent Service 不分配版本号，也不能绕过 Core 直接创建文档版本。

候选采用继续使用现有 WritingRunCommand 的幂等键和结果记录，但只把它作为 Core 操作记录：命令绑定候选版本的 `sourceTaskId`，由 Core 原子完成采用，不恢复或再次调用 Agent。这样，即使采用成功后当前版本继续前进，原 `clientRequestId` 重试仍返回第一次采用结果。

版本号属于展示序列，ReviewArtifact 自身的 `revision` 继续用于 Artifact 内部并发和评审身份，二者不能混用。

### 5. 人工版本

#### 5.1 工作稿自动保存

人工输入继续自动保存到 Outline.content 或 Chapter.content，但不创建版本。

编辑器根据完整内容 hash 判断：

- 当前工作稿是否与当前版本一致；
- 是否显示“有未提交修改”；
- 是否启用“提交版本”按钮。

#### 5.2 提交版本

用户点击“提交大纲版本”或“提交正文版本”后：

1. 前端先 flush 当前工作稿。
2. 打开提交确认弹窗。
3. 展示当前工作稿相对当前版本的 Diff、字数变化和可选备注。
4. 用户点击“确认提交”。
5. Core 校验 `expectedUpdatedAt`、完整内容 hash 和当前基础版本。
6. Core 创建 `source=manual`、`status=applied` 的新版本。
7. 新版本成为当前版本。

当前工作稿与当前版本内容完全相同时：

- 不创建重复版本；
- 不增加版本号；
- 返回当前版本并提示“没有可提交的变化”。

正文人工版本的来源规则：

- 首个正文版本要求已经存在当前大纲版本，并绑定该大纲版本；
- 后续人工正文版本继承其 `baseVersionId` 对应正文版本的 `sourceOutlineVersionId`；
- 人工编辑不会因为当前大纲后来变化，就把正文来源伪装成新的大纲版本。

因此，使用开头创建项目时，开头可以先作为正文工作稿保存，但用户需要先提交或采用一份大纲版本，之后才能提交首个正文版本。

### 6. Agent 版本

#### 6.1 版本产生时机

以下 Agent 任务成功完成时创建一个候选版本：

- 首次生成或重新生成故事蓝图；
- 生成完整正文；
- AI 修改大纲选区；
- AI 修改正文选区。

以下行为不创建版本：

- 普通创作问答；
- 全文检查报告；
- 内部正文分段生成的单个模型调用；
- Agent 运行中的 checkpoint；
- 失败、取消或被截断的任务；
- 幂等回放同一已完成任务。

#### 6.2 候选版本

Agent 候选版本：

- 任务完成即获得版本号并出现在版本历史；
- 保存完整合并后内容；
- 保存相对基础版本的 Diff；
- 不自动覆盖 Outline.content 或 Chapter.content；
- 不自动成为当前版本；
- 不自动触发下一个正文生成任务。

中短篇内容任务在候选版本成功持久化后即进入任务终态。候选版本是否被采用是独立的 Core 版本操作，不能让已完成 Agent 任务因为 `status=awaiting_user` 长期占用运行槽位，也不能通过恢复 Agent 任务来完成采用。

用户操作：

- “采用此版本”：应用到对应工作文档并设为当前版本；
- “暂不采用”：关闭本次主提示，候选版本仍留在版本历史；
- “比较”：与基础版本、当前版本或任意版本比较。

“暂不采用”不是服务端状态迁移，不修改候选版本 payload，也不物理删除版本。用户以后仍可从版本历史采用它。

#### 6.3 采用并发规则

Agent 候选版本记录任务启动时的 `baseVersionId` 和 `contentHash`。

- 当前版本仍是其基础版本时，可以直接采用该候选版本。
- 当前版本已经变化时，禁止静默覆盖。
- 用户仍要使用旧候选内容时，界面改为“恢复此内容”，重新展示它与当前版本的 Diff；确认后按恢复语义创建下一个版本号，并保留旧候选版本。
- 工作稿存在未提交修改时，采用候选版本必须被阻止；用户先提交工作稿或明确放弃工作稿。

### 7. 大纲版本与正文版本绑定

#### 7.1 正文生成门禁

“生成正文”只在以下条件同时成立时可用：

- 存在当前已提交大纲版本；
- 当前大纲工作稿与该版本内容一致；
- 正文工作稿为空，或与当前正文版本内容一致；
- 没有运行中的大纲或正文 Agent 任务；
- 目标字数在 6000～80000；
- 唯一“全文” Chapter 存在。

若大纲工作稿存在未提交修改：

- 禁止正文生成；
- 明确提示用户“请先提交大纲版本或放弃未提交修改”；
- 不能偷偷使用工作稿，也不能偷偷退回旧版本。

若正文工作稿存在未提交修改，也禁止生成或重新生成正文，避免完整候选版本绕过用户的人工改动。使用开头创建的非空正文工作稿，需要先提交为正文版本。

“重新生成正文”是独立且明确的全稿操作，必须展示将产生完整正文候选版本；它不能被选区修改、普通对话或全文检查隐式触发。

#### 7.2 来源绑定

正文任务启动时固定保存：

- `sourceOutlineVersionId`；
- 大纲版本号；
- 大纲内容；
- 大纲 `contentHash`；
- 目标总字数；
- 当前正文基础版本 ID 和 hash。

正文候选版本必须记录同一 `sourceOutlineVersionId`。任务运行期间大纲当前版本变化时：

- 已运行任务可以继续完成候选版本；
- 候选版本明确显示“基于较早的大纲版本”；
- 用户采用前必须看见该提示；
- 系统不能把来源悄悄改成新大纲。

#### 7.3 大纲变化后的正文

大纲提交新版本后：

- 现有正文版本不自动修改；
- 现有正文版本继续保留自己的来源大纲版本；
- 当前正文如果基于旧大纲，界面显示“当前正文基于大纲 vN，最新大纲为 vM”；
- 用户可以继续手动编辑、选区修改或重新生成正文；
- 系统不自动发起全稿重写。

### 8. AI 只修改选中区域

#### 8.1 启动条件

用户必须：

- 在大纲或正文 `textarea` 中选择非空文本；
- 当前工作稿没有未提交修改；
- 当前文档存在当前版本；
- 输入非空修改要求。

如果用户刚完成手动编辑，必须先提交人工版本，才能启动选区 Agent 修改。这样可以保证 Agent 版本拥有明确且不可变的基础版本。

#### 8.2 请求内容

选区修改任务保存：

```text
documentType
baseVersionId
baseContentHash
selectionStart
selectionEnd
selectedText
selectedTextHash
contextBefore
contextAfter
outlineVersionId
userInstruction
```

坐标与 hash 规则：

- `selectionStart` 和 `selectionEnd` 使用 Unicode 码点下标，`selectionEnd` 为开区间；
- Web 从 `textarea.selectionStart/selectionEnd` 的 UTF-16 code unit 下标转换为 Unicode 码点下标后再提交；
- `selectedText` 必须等于基础版本按上述码点区间取得的原始子串；
- `contentHash` 和 `selectedTextHash` 都对原字符串未经换行或 Unicode 归一化的 UTF-8 字节计算 SHA-256；
- Core 不接受落在代理项中间、越界或与原文不一致的坐标。

上下文规则：

- `selectedText` 是唯一允许改写的目标文本。
- `contextBefore` 和 `contextAfter` 只用于衔接，不得出现在替换结果中。
- 修改正文时附带基础正文版本绑定的大纲版本完整内容；即使当前大纲已经更新，也不能伪造本次局部修改的来源。
- 修改大纲时附带当前完整大纲，但明确要求只返回选区替换文本。
- 当前用户要求只出现一次。
- 不注入几十轮完整聊天历史。
- 不允许模型返回整份新文档。

#### 8.3 结果合并

Agent 只返回替换文本。Core 负责：

1. 锁定目标 Outline 或 Chapter。
2. 校验当前版本 ID 和完整内容 hash。
3. 校验选区起止位置、原文和选区 hash。
4. 使用基础版本内容执行确定性替换。
5. 验证选区外前缀和后缀逐字不变。
6. 生成完整合并后内容。
7. 创建一个 Agent 候选版本。

Agent 无权提交选区外的新内容。任何基础版本、选区或 hash 不匹配都返回版本冲突，不猜测新位置。

#### 8.4 明确边界

如果用户只选中一处把“张三”改成“李四”，系统不会自动修改未选中的其他“张三”。

用户可以：

- 继续选择其他区域修改；
- 手动修改其他区域；
- 点击“全文检查”获取潜在矛盾报告。

全文检查只报告具体位置、证据和建议，不创建版本、不自动改稿。

### 9. 正文生成

#### 9.1 用户版本语义

一次用户发起的完整正文生成任务，无论内部进行多少次模型调用，只产生一个 Agent 正文候选版本。

- 内部临时片段属于 WritingTask.graphStateJson 和 checkpoint。
- 临时片段不是 ReviewArtifact 文档版本。
- 只有完整正文组装成功、完整性校验通过并完成 Core 回调后才创建版本。

#### 9.2 篇幅策略

- 6000～15000 字：允许单次生成完整正文。
- 15000～80000 字：允许按大纲自然分段在后台串行生成。
- 内部分段不增加用户确认点。
- 用户最终只看到一个完整正文候选版本。
- 后续修改只能通过手动编辑或选区 AI 修改，不自动整稿返工。

后续分段优先读取：

- 当前已提交大纲版本；
- 当前已完成正文；
- 本轮待生成部分；
- 用户起始素材；
- 目标字数和剩余字数。

第一期不建立连续性账本。若供应商上下文容量不能承载所需完整内容，任务必须明确失败或拒绝启动，禁止静默摘要、截断或假装已读取全文。

#### 9.3 完整性

以下情况不得创建正文版本：

- `finishReason=length`；
- 内容过滤；
- 正文为空；
- 内部分段清单中存在未完成项，或分段重复、缺失、顺序错误；
- 实际正文少于 6000 或多于 80000；
- 回调或持久 checkpoint 未完成。

Core 与 Web 必须使用同一计数规则：删除 `countTextLength()` 已定义的 Unicode 空白和 BOM，再按 Unicode 码点计数。目标字数是创作目标，不另设含糊的“合理偏差”门槛；最终字数只要处于 6000～80000 的产品边界即可，界面显示相对目标的准确差值，不自动灌水或删减。结尾是否有文学上的完成感属于全文检查报告，不作为伪确定性的持久化门禁。

### 10. 版本恢复

恢复历史版本不能移动、删除或覆盖既有版本。

工作稿存在未提交修改时不能恢复。用户必须先提交工作稿，或使用普通文档保存接口把工作稿重置为当前版本内容，再重新确认恢复。

用户从当前正文 v8 恢复正文 v3 时：

1. 打开恢复确认弹窗。
2. 展示 v8 到 v3 的完整 Diff。
3. 用户点击“确认恢复”。
4. Core 以 v3 内容创建正文 v9。
5. v9 使用 `source=restore`，`baseVersionId` 指向 v8，并记录 `restoredFromVersionId=v3`。
6. Core 在同一事务中把 v9 应用到正文工作稿并设为当前版本。
7. v4～v8 和原 v3 全部保留。

大纲恢复使用相同规则。恢复后的正文继续保留被恢复内容原有的 `sourceOutlineVersionId`，不能伪造为当前最新大纲。

### 11. 版本 Diff

#### 11.1 版本入口

大纲和正文编辑器右上角提供“版本”按钮，打开统一版本抽屉。

版本抽屉包含：

- “大纲版本”和“正文版本”页签；
- 版本号；
- 当前、候选、历史等应用层标签；
- 来源：Agent、人工提交、恢复；
- 创建时间；
- 创建 Agent；
- 用户修改要求；
- 字数；
- 基础版本；
- 正文来源大纲版本；
- “比较”“采用”“恢复”操作。

#### 11.2 比较方式

支持：

- 默认比较版本与其 `baseVersionId`；
- 比较候选版本与当前版本；
- 任意选择两个同类型版本比较；
- 只显示变化；
- 返回完整 Diff，禁止静默截断。

Diff 层级：

- 大纲先按段落或行对齐，再高亮段内文字；
- 正文先按自然段对齐，只在变化段落内做细粒度高亮；
- 新增使用明确的新增语义；
- 删除使用明确的删除语义；
- 修改同时展示旧内容和新内容；
- 超长正文通过滚动或虚拟列表展示，不能裁掉尾部。

#### 11.3 Diff 生成

- 创建版本时，Core 计算并保存相对 `baseVersionId` 的默认结构化 Diff 到 `diffJson`。
- 任意两个版本比较时，Core 根据两个不可变完整 payload 计算 Diff。
- 前端只负责渲染，不根据当前工作稿重新猜测历史内容。
- Diff 响应包含 fromVersionId、toVersionId、字数变化和有序差异块。

### 12. 当前版本与工作稿同步

当前版本发生变化时：

- 采用 Agent 版本、提交人工版本或确认恢复都必须推进当前版本。
- 采用和恢复必须在同一事务中更新对应 Outline.content 或 Chapter.content。
- 前端收到成功响应后更新编辑器内容和 `expectedUpdatedAt`。
- 失败时保留原工作稿和原当前版本。
- 不允许出现版本已标记当前但正式工作文档仍是旧内容的部分成功。

当前版本由 Core 在同一 `artifactKey` 下选择 `status=applied` 且 `versionNumber` 最大的版本；`appliedAt` 只用于审计和展示。不能由前端按数组最后一项或时间戳猜测。

### 13. 公共 API

#### 13.1 版本读取

新增：

```text
GET /api/v1/novels/{novelId}/versions?documentType=outline|manuscript
GET /api/v1/novels/{novelId}/versions/{versionId}
GET /api/v1/novels/{novelId}/version-diff?fromVersionId=...&toVersionId=...
```

全部接口校验登录用户和小说归属。正文版本同时校验 Chapter 归属。

版本列表只返回版本号、状态、来源、字数、基础版本、来源大纲版本和时间等元数据；完整 `content` 由版本详情接口按需返回，且禁止截断。

#### 13.2 人工提交

新增：

```text
POST /api/v1/novels/{novelId}/versions
```

请求至少包含：

```text
clientRequestId
documentType
chapterId
baseVersionId
expectedUpdatedAt
contentHash
summary
```

Core 从当前 Outline 或 Chapter 读取完整工作稿，客户端不重复上传另一个可能漂移的完整正文副本。

#### 13.3 候选版本操作

新增：

```text
POST /api/v1/novels/{novelId}/versions/{versionId}/adopt
POST /api/v1/novels/{novelId}/versions/{versionId}/restore
```

- `adopt`：采用未过期候选版本。
- `restore`：创建新的已应用版本并成为当前版本。

所有写请求包含 `clientRequestId` 和当前基础版本 ID，使用幂等与并发校验。

#### 13.4 Outline 手动保存

扩展现有 Outline 更新接口，不重复注册路由：

```text
PUT /api/v1/novels/{novelId}/outline
```

请求包含：

```text
content
expectedUpdatedAt
```

响应返回最新 `updatedAt` 和 `contentHash`。

#### 13.5 契约和客户端

公共接口先修改 FastAPI/Pydantic 契约，再运行：

```bash
npm run api:generate
npm run api:check
```

Web 只能使用生成客户端类型，不手写重复 DTO。

### 14. Agent 运行与提示词

中短篇不新增 Agent 身份，只增加篇幅 Profile 对应的 Operation brief 和上下文策略。

#### 短篇创作原则与来源策略

中短篇 Operation brief 统一遵循：

- 先建立开头承诺、当下压力、人物选择、不可逆变化、高潮选择和结局兑现，不套用长篇的阶段、章节组或 Beat Plan；
- 6000～15000 字默认单主线和少量关键人物；篇幅增长时才允许增加自然分节和服务主线的副线；
- 场景必须由上一场的行动或后果推动，不能靠无关设定和说明性段落灌水；
- 当前版本内容和本轮用户要求高于旧对话，禁止用历史聊天覆盖用户已经确认的文本。

起始素材按类型处理：

- `idea`：补出核心冲突、关键选择和结局方向，不擅自扩大为长篇世界观；
- `opening`：把原文作为固定前缀，分析其视角、语气、承诺和悬念，再向后规划；
- `ending`：把原文作为固定后缀，从最终结果和情绪余味反推必要因果；
- `outline`：保留用户明确事件和顺序，只补足必要的因果、压力和转折；
- `mixed`：按用户已有标签识别灵感、开头、结尾和大纲片段；不能确定的内容作为可编辑假设写入蓝图，不反复追问。

用户后来通过人工版本或选区 Agent 版本明确改过某段文本时，当前版本内容成为后续修改的权威，旧起始素材不能把它改回去。

#### 蓝图生成

- 读取用户起始素材原文和目标字数。
- 输出完整可编辑蓝图。
- 不要求阶段、剧情单元、章节组或 Beat Plan。
- 不自动调用其他 Agent 返工。
- 成功后创建一个大纲候选版本。

#### 正文生成

- 只读取固定的来源大纲版本。
- 不读取未提交工作稿。
- 首次从 `opening` 生成时保留已提交开头正文作为固定前缀，从 `ending` 生成时保留起始结尾作为固定后缀。
- 重新生成是用户显式发起的完整候选版本；除已确认的开头、结尾约束外，不承诺保留旧正文的未选中区域。
- 内部分段时保持一个用户任务和一个最终候选版本。
- 不自动编辑或校验返工。

#### 选区修改

- 只读取当前版本、选区、前后上下文、本次正文基础版本绑定的大纲版本和本轮要求。
- 只返回替换文本。
- 不输出完整文档。
- 不修改选区外内容。

#### 全文检查

- 编辑 Agent 只报告开头承诺、结构、节奏、高潮和结局问题。
- 校验 Agent 只报告人物、时间线、设定和因果矛盾。
- 报告必须给出具体原文位置、证据和修改建议。
- 报告不创建文档版本，不自动改稿。

提示词必须保持“短静态身份 + Operation brief + 当前权威内容”，不能为本功能把所有版本和修改规则堆入五个全局 system prompt。

### 15. 错误与并发

- 工作稿版本冲突：返回 409，保留本地输入并要求用户处理。
- 提交版本时基础版本已变化：返回 409，不创建版本。
- Agent 选区任务基础版本已变化：任务失败，不猜测选区新位置。
- 候选版本采用时基础版本已变化：要求按恢复语义创建新版本，不能覆盖当前版本。
- 恢复时当前版本已变化：重新展示基于新的当前版本的 Diff 后再确认。
- 相同版本写入 `clientRequestId`：返回第一次结果。
- 相同 Agent taskId/jobId 完成回放：返回原候选版本。
- Redis 或回调暂时失败：依赖现有持久命令和任务恢复，不重复生成版本。
- Diff 计算失败：版本仍保留，但不能谎称 Diff 可用；返回明确错误并允许重试计算。
- 版本内容或 Diff 不得静默截断。
- 通用 ReviewArtifact 创建、批准、返工或丢弃命中 `short-medium:*` 时返回明确错误，不能绕过版本服务。

### 16. 前端设计

中短篇在现有 WorkspaceShell 内使用简化外壳，不复制失败实现中的大型独立作家室。

桌面主区：

```text
┌──────────────────────────────────────────────────────────────┐
│ 蓝图 | 正文       当前版本 / 未提交修改       版本   提交版本 │
├───────────────────────────────────────┬──────────────────────┤
│                                       │ 当前 Agent 会话       │
│ 可编辑大纲或完整正文 textarea         │                      │
│                                       │ AI 修改选中内容       │
│                                       │ 生成正文 / 全文检查   │
└───────────────────────────────────────┴──────────────────────┘
```

版本抽屉从右侧打开，不长期占用第三栏。关闭版本抽屉后仍保留工作稿、选区和会话状态。

按钮规则：

- 无选区时禁用“AI 修改选中内容”。
- 没有当前大纲版本且大纲工作稿为空时显示“生成蓝图”；大纲工作稿已有内容时优先显示“提交大纲版本”。
- 有未提交修改时启用“提交版本”。
- 没有变化时禁用“提交版本”。
- 大纲有未提交修改时禁用“生成正文”。
- Agent 运行期间禁用冲突操作，但不清空用户尚未提交的输入。
- 同一上下文只突出一个主按钮。

## 影响范围

## 验收标准

### 创建与篇幅

- [ ] 5999 和 80001 字被拒绝。
- [ ] 6000 和 80000 字被接受。
- [ ] 中短篇不再展示 8～25 章承诺。
- [ ] 灵感、开头、结尾、简纲和混合素材均能创建项目且原文不截断。
- [ ] 中短篇创建唯一“全文” Chapter。
- [ ] 长篇创建行为不变。

### 工作稿

- [ ] 大纲和正文均能手动编辑。
- [ ] 两者均按 1.2 秒自动保存工作稿。
- [ ] 自动保存不会创建版本。
- [ ] 刷新后可以恢复未提交工作稿。
- [ ] 版本冲突不覆盖本地输入。
- [ ] Outline 保存使用扩展后的既有路由，不注册重复路径。

### 人工版本

- [ ] 点击提交前不会创建版本。
- [ ] 提交确认弹窗显示完整 Diff 和字数变化。
- [ ] 点击确认后只创建一个人工版本并设为当前。
- [ ] 相同内容重复提交不创建新版本。
- [ ] 幂等重试不增加版本号。

### Agent 版本

- [ ] 一次成功 Agent 文档任务只创建一个候选版本。
- [ ] 内部分段模型调用不创建版本。
- [ ] Agent 失败、取消或截断不创建版本。
- [ ] 候选版本不自动覆盖工作稿。
- [ ] 用户采用后才成为当前版本。
- [ ] 暂不采用不会删除或修改候选版本。
- [ ] 候选版本持久化后 Agent 任务结束，不长期占用运行槽位。
- [ ] Agent 任务重放返回同一版本。
- [ ] 通用 ReviewArtifact 的 revise、discard 和 approve 不能改写或删除中短篇文档版本。

### 大纲与正文绑定

- [ ] 正文生成只使用当前已采用的大纲版本。
- [ ] 大纲有未提交修改时不能生成正文。
- [ ] 正文有未提交修改时不能生成或重新生成正文。
- [ ] 每个正文版本显示来源大纲版本。
- [ ] 大纲后来变化不会自动修改已有正文。
- [ ] 基于旧大纲完成的候选正文有明确提示。

### 选区修改

- [ ] 无选区不能启动 AI 修改。
- [ ] 有未提交人工修改时不能启动 AI 修改。
- [ ] Agent 只返回替换文本。
- [ ] Core 校验基础版本、完整 hash、选区位置和选区 hash。
- [ ] 中文、换行和辅助平面字符场景下，Web 与 Core 对选区码点坐标和 hash 的结果一致。
- [ ] 候选版本的选区外内容与基础版本逐字一致。
- [ ] 正文选区候选版本继承基础正文绑定的大纲版本。
- [ ] 过期选区明确失败，不自动搜索相似文本替换。
- [ ] 用户采用前可以查看完整 Diff。

### 恢复

- [ ] 恢复历史版本创建新的更高版本号。
- [ ] 恢复不删除中间版本。
- [ ] 恢复前展示相对当前版本的 Diff。
- [ ] 有未提交工作稿时不能直接恢复。
- [ ] 恢复后的正文保留真实来源大纲版本。
- [ ] 恢复与工作文档更新在同一事务内完成。

### Diff

- [ ] 版本抽屉分别展示大纲和正文版本。
- [ ] 默认可以比较版本与基础版本。
- [ ] 可以任意选择两个同类型版本比较。
- [ ] 大纲按段落/行、正文按段落和段内文字显示差异。
- [ ] 8 万字正文 Diff 可以查看到尾部。
- [ ] Diff 和版本内容不静默截断。

### 恢复与并发

- [ ] Agent 任务可从最后 checkpoint 恢复且不重复生成版本。
- [ ] 同一文档并发提交只允许一个基于当前版本成功。
- [ ] 人工提交和恢复的 `clientRequestId` 重试返回第一次创建的版本。
- [ ] 候选采用的 `clientRequestId` 重试返回第一次采用结果。
- [ ] 采用过期候选不会覆盖新当前版本。
- [ ] 任何部分失败都不会出现版本已当前但工作文档未更新。

### 真实流程

- [ ] 使用灵感生成大纲候选、采用、生成正文候选并采用。
- [ ] 灵感、开头、结尾和混合素材在无大纲版本时都能通过“生成蓝图”进入流程。
- [ ] 使用开头创建工作稿，人工提交大纲和正文版本。
- [ ] 使用开头生成正文时原文保持为固定前缀。
- [ ] 使用结尾生成蓝图和正文时原文保持为固定后缀。
- [ ] 使用简纲进行两轮人工提交和两轮 Agent 选区修改。
- [ ] 对同一正文完成候选采用、人工提交、历史恢复和任意版本 Diff。
- [ ] 验证所有未选中区域在 Agent 修改后逐字不变。

## 实施分期

### 第一阶段：双文档与人工版本

- 修正 6000～80000 篇幅。
- 完成中短篇创建和唯一“全文” Chapter。
- 完成可编辑 Outline、工作稿自动保存和人工提交版本。
- 完成版本列表、详情、当前版本和基础 Diff。

第一阶段结束时，用户不依赖 Agent 也能完成大纲、正文、提交版本、查看历史和恢复。

### 第二阶段：Agent 候选版本与选区修改

- Agent 蓝图和正文任务生成候选版本。
- 完成采用、暂不采用和过期候选恢复处理。
- 完成选区请求、只返回替换文本、Core 确定性合并。
- 完成 Agent 版本 Diff。

### 第三阶段：长正文生成与真实验收

- 完成 15000～80000 字内部串行分段和 checkpoint 恢复。
- 完成正文来源大纲版本绑定和过期提示。
- 完成可选全文检查报告。
- 使用四类起始素材运行真实端到端流程。

每个阶段都必须形成可运行、可测试的纵向能力。不得先铺设大量不可使用的协议和 UI，再等待最后一次性联调。
