实施事实与剩余边界见：[实施规格](2026-09-10-video-episode-production-implementation.md)、[分批计划](../plans/2026-09-10-video-episode-production-rebuild.md)。开发实现完成不自动授权真实调用、服务器退役迁移或生产发布。

## 1. 产品承诺与第一批范围

帮助独立小说作者将故事改编成可以连续更新的剧集，并在反复修改中保留满意成果，清楚管理尚未完成的决定、制作成本和交付版本。

第一批交付到：独立分集、多章取材、单集剧本工作稿与批准、剧本派生分镜、改动影响复核以及明确的成果沿用。现有素材与制作能力按新的分集身份接入；生成、声音制作和导出不另建第二套执行系统。

当前代码已实现相接分集、跨章取材、剧本与分镜工作稿／正式版、修改影响和制作沿用所需的完整对象及入口。A／B／C 三场景已在本地隔离 PostgreSQL 中通过公共 API、浏览器断言和媒体探测完成组合验收。该结果只证明无供应商调用时的业务、媒体与恢复链。

不纳入第一批：高级非线性剪辑、完整角色声音引擎、自动多镜视频编辑、自动连续性修复、多项目素材市场、公开商业计费和生产开放。最终视频供应商方向仍为即梦／Seedance 2.5；其真实调用继续暂停。图片、音频及模型效果使用固定演示素材验证产品交互，不能据此宣称真实画质、音色一致性或供应商计费已通过验收。

首批产品形态验证需分别记录旁白主导与对白主导的素材准备和声音要求；以一个样例通过不能证明两种表现形式均可交付。项目中的时长和表现形式用于创作约束，不把平台建议或供应商单次时长当成分集叙事规则。

## 2. 工作台与主要操作

视频入口改为小说下的“剧集制作”。主导航是分集列表，章节在取材面板查看。集号只表示展示顺序，调序、改名或更换来源不改变这集的身份。

首屏展示集名、故事摘要、当前创作位置、待处理决定与最近制作／交付版本。进度来自已保存的业务事实，不以任务数量计算虚假的完成百分比。空项目提供“新建一集”，不要求先规划整部剧。

单集以两个主要工作面组织第一批交互：

- **剧本**：本集概要、场次、动作、对白、旁白、来源对照和承接依据。场次的地点与时间、出场角色属于可展开信息，普通作者无需先填写镜头术语。
- **分镜与制作**：按剧本场次查看镜头，选中镜头后就地查看参考、声音意图、提示词、关键帧和候选。保持选中对象与前后镜上下文，制作工具不再要求作者跨多个全局页签寻找同一镜头。

取材、系列设定和修改影响作为上下文面板；粗剪、声音和成片作为本集后续制作视图。阶段可以回访，允许剧本已有新版而制作仍基于原版。

### 2.1 单集起草

1. 作者新建一集，填写或由系统建议标题、目标时长和本集创作意图。
2. 选择一个或多个章节中的段落，或手工起草。每份来源分别保留章节身份、原文快照和范围，不把多章拼成无法区分来源的长字符串。
3. AI 可以提出剧本候选；作者采用为工作稿后编辑。保存草稿不代表批准或产生正式分镜。
4. 剧本包含同一版本下的本集概览和场次，不额外制造一份需要同步维护的分集大纲。场次以可见行动及明确说话人的台词表达故事。
5. 作者确认剧本和必要的结尾状态，再由该版本派生分镜候选。剧本批准与分镜批准是两个不同的决定。

### 2.2 下一集

“新建下一集”只确定创建顺序。系统展示可引用的前集结尾，但作者需要明确采用哪个场次、哪个版本以及哪些状态。

顺叙场可以引用“顾舟持有未拆封的信”；回忆场可以独立指定“三日前，信仍在林岚手中”。一段回忆不会覆盖当前时间线状态，也不会因物理集号相邻而自动继承。

### 2.3 返工

作者从剧本场次、镜头或审片问题进入修改。工作区先表明要改变什么、希望保留什么，再展示新草稿及影响。

影响分成三类：直接依据变化、可能的剧情连带影响、经作者复核后沿用。缺少直接引用不能自动推断为无影响；轻微文字变化也不能默认要求整集重做。

确认新剧本后，待复核列表成为新的工作入口。原分镜、选片、粗剪、声音和成片保持可读，当前制作基线不自动替换。用户逐项处理后确认新的制作版本组合。

## 3. 四种不同的版本决定

| 对象 | 作者作出的决定 | 不产生的隐式效果 |
| --- | --- | --- |
| 工作草稿 | 保存正在尝试的表达 | 不替换正式剧本，不使后续集立即改写 |
| 正式剧本 | 确认本集的新改编内容与必要状态 | 不清空制作成果，不自动花费生成费用 |
| 制作基线 | 明确采用哪些剧本、分镜、定妆、声音和素材版本 | 不修改原始素材及其生成依据 |
| 交付版本 | 确认一份实际成片及其冻结制作清单 | 不随上游 head 或默认设定变化 |

界面可以同时显示“剧本 v2 已确认，制作仍依据 v1，成片 v1 已交付”。已有制作基线仍可用于明确标注版本的再次导出，不能为了使用最新剧本而拼接所有对象的最新 head。

## 4. 三个核心场景

以下为虚构演示素材，不涉及用户真实小说。角色为林岚和顾舟，道具为密封信。

来源：第 12 章《雨中来信》包含雨夜赴约与三日前收到师父密信的回忆；第 13 章《桥下交接》包含试探和交信；第 14 章《封蜡》包含顾舟拆信。

### 场景 A：制作第一集《雨夜交信》

| 作者看到什么 | 操作 | 得到什么 |
| --- | --- | --- |
| 空的分集列表 | 新建一集，选择第 12、13 章的有关段落 | 独立分集与可核对的来源集合 |
| 雨中赴约、桥下试探、交出密信三场候选 | 采用为工作稿，调整动作与对白 | 可恢复的剧本草稿 |
| 结尾为林岚交出信；顾舟持有密封信、尚未拆封 | 确认剧本和结尾状态 | 剧本 v1 与可供后续明确引用的依据 |
| 按三场组织的镜头候选 | 审核分镜，选择适用参考 | 分镜 v1 与明确的制作基线 |
| 固定素材代表的制作结果 | 确认采用并查看本集组合 | 演示中的采用决定；真实成片验收另行进行 |

### 场景 B：创建第二集《拆信》

| 作者看到什么 | 操作 | 得到什么 |
| --- | --- | --- |
| 新集草稿与第一集已确认的结尾 | 明确引用“顾舟持有未拆封信” | 绑定第一集剧本 v1 及具体状态的承接关系 |
| 第 14 章拆信段和第 12 章三日前的回忆 | 选择素材，先安排回忆再回到雨夜 | 独立保留的两组来源与时间说明 |
| 回忆中林岚持信；雨夜顾舟持信 | 核对每场的时间和依据，确认剧本 | 第二集剧本 v1；回忆不改变当前雨夜状态 |

### 场景 C：第一集改为收回信件

| 作者看到什么 | 操作 | 得到什么 |
| --- | --- | --- |
| 第一集已有剧本和制作基线 | 修改交信场，提出“林岚因不信任顾舟而收回信” | 新草稿；正式 v1 和既有制作继续保留 |
| 顾舟持信变为林岚仍持信；本场镜头与第二集开信场依赖旧状态 | 查看差异，确认新版剧本 | 第一集剧本 v2 与待复核事项；制作仍依据 v1 |
| 雨中赴约等未变部分、本场需修改部分、第二集承接问题分别可见 | 检查后沿用未变成果，单独处理本场 | 有依据的沿用决定；不自动复用所有素材 |
| 第二集开信场失去原承接依据 | 打开相关场次，改为“顾舟追上林岚索要信件”并确认 | 第二集新版剧本及更新的承接关系 |
| 三日前收到师父信件的回忆与本次修改无直接关系 | 复核后保留该场 | 不因当前信件归属变化而整集推翻 |

系统允许作者保留不同的剧情分支，但需要明确分支／承接依据。不能用“忽略提示”把实际矛盾伪装成已经解决。

## 5. 最低必要的业务关系

具体表名与 API 路径已经在实施规格和版本化契约中落地；下列关系仍是判断实现是否正确的产品依据，不将对象数量机械等同于表数量。

- 项目拥有独立 Episode；来源章节不是 Episode 的父对象。
- Episode 保存来源集合版本；集合内的快照各自保留来源身份与范围。
- 剧本版本拥有稳定场次与台词身份。编号、排序和显示名称不承担版本对应关系。
- 分镜版本明确依据哪份剧本；镜头具有稳定逻辑身份及不可变内容版本。
- 生成素材保存原始生成依据与媒体事实；采用决定记录该素材被本次制作如何使用，不能回写原始生成清单。
- 制作基线引用明确版本组合；交付版本冻结实际采用区间、声音、字幕与输出决定。
- 跨集承接引用某个已确认版本中的具体状态，并区分叙事时间。新一集不读取“角色当前最新状态”来隐式解释旧剧情。

首批沿用限定同一集并显式确认。系统比较相关剧本内容、表演／声音意图、参考素材和生成参数；检查依据、作者决定和被采用对象都要保存。人物知情程度等语义变化可能影响未改文字的镜头，需要作者复核，不能只用文本哈希证明可用。

小说原文更新只提示存在新来源。作者选择同步后创建新的来源集合和剧本草稿；旧来源范围仍解释在原快照上。

系列默认定妆、剧情状态、实际采用素材分开保存。对白绑定说话人和台词身份；角色音色依据与实际音频片段分开。原生音视频中的声音变化可能要求复核整个片段，不能承诺只改音频必然保住画面。

## 6. 旧实现的取舍

| 旧对象或能力 | 处理原则 |
| --- | --- |
| 章节改编根、章节内镜头断点分集、方案版本加集序号表示一集 | 退出新的业务入口与公共语义 |
| 确认方案后清空当前分集及下游入口 | 改为保留原制作基线并建立影响复核 |
| Take 只能按生成时的方案被采用 | 分开原始来源与当前采用关系，不改写旧素材 |
| 粗剪每个正式镜头必须恰好出现一次 | 不作为新产品规则；完整性通过明确采用和删改决定保证，基础剪辑实施另列子项 |
| 现有拆镜、审镜、视觉编辑、候选播放组件 | 已按新 Episode 对象和来源重接；旧工作区组件退出运行入口 |
| 来源冻结、作者批准、权限与归属、耐久执行、存储和媒体处理 | 通用原则已由新领域实现复用，并通过定向、全量及组合 E2E 验证 |
| 前一轮 V0.1／V0.2 补丁 | 已完成逐项审计；适用能力已吸收或改写，旧入口与运行装配已退出 |

新业务只提供一条制作主链。旧视频结构可按依赖清单替换，不长期维护两套新建和修改语义；共享的小说、设定、审核及耐久执行能力不得因此被随意删除。

## 7. 实施结果与收口顺序

1. **P0 已完成**：产品范围、对象关系、公共契约、AI 输出 Schema、迁移边界和 A／B／C 固定场景已经冻结。
2. **P1 已完成**：独立分集、多章来源快照、剧本工作稿 CAS、AI 候选、正式批准、承接关系和前端／CLI 恢复入口已经落地。
3. **P2 已完成**：稳定 Shot／ShotVersion、分镜局部修订、影响复核、TakeAdoption 和不可变 ProductionBaseline 已接通；范围外镜头由 Core 保留。
4. **P3 已完成**：视觉定妆、提示词、关键帧、Episode 原生逐镜任务、simulated placeholder MP4、Take、粗剪、声音字幕和整集导出已经形成纵向链。

6. **最终仓内收口已完成**：A／B／C 组合 E2E、完整 `./mvnw verify`、Python、Web、静态检查和契约检查均已完成；证据见 [最终验收记录](../audits/2026-09-10-video-episode-production-final.md)。

## 8. 验收条件与当前证据

产品验收条件保持不变：

- A、B、C 三个场景完整成立，作者始终知道正在编辑哪一集、依据哪一版，以及下一项需要决定的事。
- 集号和章节选择变化不改变分集身份；一集多来源和一来源用于多集均可追溯。
- 工作稿可保存恢复；批准新版剧本不改变当前制作基线，不清空旧成果。
- 改动影响包括直接依赖和可能的剧情连带影响，作者能查看依据、保留成果并逐项处理。
- 显式沿用真实建立采用关系；不能靠修改原 Take 清单或放松归属校验实现。
- 第二集承接第一集某个已确认状态，回忆可采用独立依据；上游变化不会静默改写下游剧本或成片。
- AI 候选、人工修改、批准、生成和采用分别留存；模拟产物明确标记为 simulated_placeholder，不冒充真实供应商结果。

当前已通过的分层证据：

- 视频公共 OpenAPI 为 56 个路径、67 个操作，Java VideoApi 保留 11 个 Project／Asset／VisualCanon／provider-asset 共享操作；
- Durable Agent V2 Catalog 共 23 项，其中视频只保留 4 项 Episode 剧本／分镜候选操作；
- 完整 `./mvnw verify` 通过：服务鉴权 11 项、服务契约 5 项、Core 1,248 项（3 项按预期跳过）、Java CLI 145 项；
- Python 全量 5,864 项通过、3 项跳过；Ruff 与 310 个源文件的 Mypy 检查通过；
- Web 测试 371 项及生成客户端测试 3 项通过，typecheck、lint 与 `api:check` 通过；
- P4 retirement 在隔离 PostgreSQL 完成正向、幂等、legacy-only 行拒绝、共享表旧分支拒绝和 RESTRICT 中途失败整事务回滚。
- A／B／C 组合 E2E 通过，证据、浏览器截图和模拟成片见 [最终验收记录](../audits/2026-09-10-video-episode-production-final.md)。

以上均为仓内或本地隔离模拟验收。真实 Seedance 画质、音色、用量和付费没有验收，服务器数据库和生产开关没有改动。

## 9. 源码依据

当前落地的主要依据包括：

- `apps/web/src/features/video/production/`：唯一 Episode 工作区，包含取材、剧本、分镜、影响、制作、后期与交付界面；
- `apps/core-api/src/inkforge_core/video/episodes/`：公共 Pydantic/OpenAPI 权威；旧 chapter-adaptation、render/take/post 路径已移除；
- `apps/core-api-java/src/main/java/cn/inkforge/core/video/`：Episode、制作基线、逐镜生成和后期的事务、CAS、幂等与受控文件实现；
- `apps/agent-service/src/inkforge_agents/execution/video_episode.py` 与 `video_storyboard.py`：剧本和分镜 V2 生成／局部修订；
- `scripts/migrations/20260910_video_episode_script_domain.sql` 与 `20260910_video_production_baseline_domain.sql`：P1/P2 开发结构；
- `scripts/migrations/20260910_video_legacy_domain_retirement.sql`：仅隔离演练的失败关闭退役脚本。

旧 `JooqVideoAdaptationRepository`、`JooqVideoRenderRepository`、`JooqVideoPostProductionRepository`、Python `VideoRepository` 中的 Scene 方法和相应生成 jOOQ 类型目前没有运行装配，但源码仍在。服务器实际晋升物理退役时必须和 schema-contract／jOOQ 一起删除或重导，不能把“路由不可达”写成“旧结构已经从服务器消失”。
