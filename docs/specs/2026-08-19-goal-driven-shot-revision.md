# 目标驱动分镜与正式方案修订

状态：开发库实现完成；真实 v1 修订候选等待作者处理，正式 Head 未切换
日期：2026-08-19

## 1. 背景

章节影视化 v2 已经完成“章节原文 → Scene → DramaticBeat → Shot → 用户确认”的基本闭环，但真实章节验证暴露了新的产品问题：

- 确定性门禁把“新场景首镜必须是建立/氛围镜头且景别足够宽”作为硬规则；
- Agent 物化阶段会直接把不符合模板的首镜改成 `establishing`，同时扩大景别和改写切镜理由；
- 平均镜头时长、慢镜比例、补充镜头用途等经验规则会直接拒绝候选；
- `adaptationType` 同时表达原文关系和视听手法，`audioMode` 同时表达对白位置和环境声，导致来源、画面与声音职责互相污染；
- 正式方案确认后只能重新从章节生成，不能以当前正式版本为基线产生可审核的 v2 修订候选。

这些实现能够阻止最初的“按句拆镜”，但也会把具体样本的诊断结论固化为通用电影模板。镜头标签正确不等于画面真的完成空间交代，平均时长合规也不等于节奏成立。

## 2. 产品结论

章节改编改为“目标驱动”，而不是“镜头语法规则驱动” ：

```text
章节原文
  → 场景与戏剧节拍
  → 每个节拍的观众覆盖目标
  → 镜头时间线
  → 非阻断审镜建议
  → 作者编辑与确认
```

覆盖目标描述观众在一个节拍中必须或最好获得的信息、行动、情绪、空间关系、人物关系、视觉母题或转场感受。镜头是完成目标的手段，不要求一个目标对应一个镜头，也不要求一个镜头只完成一个目标。

系统不再要求每个新场景第一镜必须是建立镜头。只有当节拍明确存在空间覆盖目标、但没有镜头承担时，才提示“空间关系尚未覆盖”。同一运动镜头可以先交代空间再完成动作，不需要为了符合标签额外插镜。

## 3. 目标

1. Agent 第一阶段除 Scene/Beat 外，明确生成节拍覆盖目标。
2. 每个新生成镜头说明“本镜作用”“观众获得”以及承担哪些覆盖目标。
3. 把来源关系、镜头用途、对白位置和声音设计拆成独立维度。
4. 电影语法、节奏和冗余检查改为有证据的非阻断建议；结构、来源和版本一致性仍为硬约束。
5. 用户可基于当前正式方案启动 AI 修订，得到新的 ReviewArtifact 候选；正式旧版本保持不可变。
6. 用户编辑候选时可查看目标覆盖情况、调整镜头承担目标，并最终自行确认。

## 4. 非目标

- 不调用即梦视频生成接口。
- 不实现跨服务的局部 patch；AI 修订仍返回完整候选，界面和文案不得伪装成只修改了局部数据库行。
- 不自动采用 AI 修订，不静默覆盖正式方案。
- 不要求用户理解导演、摄影或剪辑专业术语才能完成审核。
- 不把审镜建议做成不可解释的总分或一票否决。

## 5. 领域设计

### 5.1 节拍覆盖目标

每个 `DramaticBeat` 新增有序 `coverageGoals`：

- `goalKey`：方案内连续 `G01..GNN`；
- `kind`：`story_information | action | emotion | space | relationship | motif | transition`；
- `priority`：`essential | supporting`；
- `description`：面向观众的自然语言目标。

`kind` 只用于扫描和审镜分组，不决定镜头类型、景别或时长。一个镜头可承担多个目标，一个目标也可由多个镜头共同完成。

### 5.2 镜头职责

每个新镜头增加：

- `storyFunction`：为什么需要这个镜头；
- `audienceGain`：镜头结束后观众新增的信息、情绪或空间认知；
- `coveredGoalKeys`：本镜承担的所属 Beat 目标。

`narrativePurpose` 继续作为便于扫描的软标签，不再作为电影语法门禁。用户新增镜头后可以没有目标绑定，但界面必须提示“尚未说明承担目标”，不能为了通过校验伪造绑定。

### 5.3 来源关系

公共候选不再使用含义混杂的 `adaptationType`，改为：

- `sourceRelation=direct`：直接呈现来源事件或明确文字，至少一个来源范围；
- `sourceRelation=derived`：由来源合理视觉化推导，至少一个来源范围；
- `sourceRelation=supplemental`：为视听表达补充，不改变原著事实，可以有用于说明上下文的来源范围，也可以没有独立原句。

“镜头用途”和“是否有独立原句”保持独立。建立、反应、插入、氛围都可以有来源；无来源镜头也不自动等于空镜。

开发库为兼容既有正式 v1 行保留内部旧 `adaptationType` 列，新写入同时保存新的 `sourceRelation`；公共 API、Agent 和前端只使用新字段。

### 5.4 对白与声音

公共候选把旧 `audioMode` 拆为：

- `speechMode=none | sync | offscreen | voiceover`；
- 可空 `spokenText`：实际说出的文字；
- `soundDesign`：环境声、音效、音乐和静默任务。

对白和环境声可以同时存在。新生成结果中，`speechMode != none` 时必须提供 `spokenText`；没有对白时不得虚构台词。开发库保留旧 `audioMode/audioIntent` 作为既有正式数据兼容列，新写入由 Core 确定性映射。

### 5.5 审镜发现

候选保存一次结构化初审：

- `reviewSummary`；
- `reviewFindings[]`：`severity=notice | warning`、作用域 Key、问题、证据和建议。

发现只向用户解释风险，不阻止确认。用户本地编辑后，界面明确标记初审基于 AI 原始候选；确定性目标覆盖提示则随编辑实时重算。

### 5.6 紧凑型即梦提示词与人物表情

真实样本表明，把旧版简洁主线与新版表演、表情、声场、连续性全部作为必填段落，会把一个镜头扩写成字段说明书。
新生成的 `ShotPromptSpec` 因此只请求当前镜头真正需要的六类事实：

- `subjectAndScene`：当前构图中必须识别的主体、地点和最小设定锚点；
- `visibleAction`：一个主要可见变化；
- 可空 `expressionAndGaze`：当前景别确实可见且对本镜有叙事作用的表情或视线；
- `camera`：已确认的一个机位和一个主要运动；
- `audio`：已确认对白与必要环境声；
- `negativeConstraints`：最多三条、只保护容易漂移的关键事实。

既有 `performance/continuity` 字段只用于解析历史 v2 候选；新模型 Schema 不再请求这两个字段。人物表演并入
`visibleAction` 或 `expressionAndGaze`，当前镜头的结束状态写在动作结果中，不再用自由连续性段落复述前后镜剧情。

- 中景及更近景别可以描述一个可见表情变化或一个明确视线目标；
- 全景/大全景只能描述头部朝向、步态或身体张力，不得要求看清疤痕、瞳孔、嘴唇等微表情；
- 物件、无人空镜和只见手部的插入镜头必须令 `expressionAndGaze=null`，最终文本不得输出“无人物表情任务”；
- 冻结设定中的事实还必须经过“本镜必要”筛选，不能因为合法就把完整服装、道具机制或世界观全部复制到本镜；
- 当前正式镜头事实优先于单项设定，单项设定优先于世界观风格；道具设定里的动态状态只有在本镜正式动作或来源明确发生时才能进入候选；
- 批量生成时按 `shotKey` 分别构造设定投影，不能把一个目标镜头命中的人物、地点或道具设定共享给同批其他镜头；
- 人物外观再按景别裁剪：特写/近景只给画面可见的头面或本镜明确提及锚点，中景逐步加入上身服装，全景才允许完整造型；
- 一个正式主动作可以包含其直接可见结果，但不得凭空追加“再次、继续、回拧、重试”等失败后的第二次尝试；
- 生成动作中的转动、旋转等物理变化必须能在本镜正式事实或来源找到依据，道具静态设定不能被改写成当前动作；
- 每个目标同时提供正式景别代码与产品中文标签；模型不得把 `close=近景` 自行收紧为“特写”，或以其他景别词改写已确认构图；
- 每个字段只承担一个职责，同一动作、服装和场景事实不得跨字段重复；
- 空间建立镜头默认使用能读清纵深关系的构图，不得无理由用长焦压平空间。

按正式时长限制信息预算：

- 500～2500ms：一个主要变化，编译文本不超过 360 字；
- 3000～5000ms：一个主要变化加一个可读反应，编译文本不超过 480 字；
- 5500～15000ms：仍保持单一连续镜头，编译文本不超过 640 字。

字符预算是生成候选的可执行性门禁，不允许静默截断。画幅和时长由编译器持有，模型字段不得重复；负面约束不得
禁止完成本镜正式动作所必需的手部、身体局部或正式主体；“其他人物/额外人物”仍可用于防漂移。模型候选先经过一次有边界的确定性归一：移除编译器元数据与历史
冗余字段、清空当前景别不可见的表情、删除与正式动作直接冲突的负面约束。归一不得截断正文、改写动作、补造事件
或改变镜头意图。单一冲突的显式景别词属于技术标签，可确定性改为正式中文景别；正式标签与一个冲突标签并存但没有
推拉、切换或景别变化语义时可删除冲突标签，主体与摄影机重复景别时只在摄影机保留。真正涉及景别变化时不得自动
改写。归一后仍有问题时，同一任务只允许一次带具体原因的完整纠正。第二次仍有 Schema、目标顺序、空字段、
编译失败或超预算等硬错误时明确失败并返回可定位原因；动作密度、跨字段重复、邻镜语言、不可见解释、未确认状态变化
等语义质量问题不得把整个任务判死，必须随候选保存为 `qualityWarnings`，由用户确认或手动修改。

## 6. 硬约束与软评估

### 6.1 硬约束

仅保留：

- Scene、Beat、Shot、Goal Key 连续且父子引用有效；
- 时间线、来源范围和章节哈希有效；
- `direct/derived` 至少绑定来源，补充镜头不得改变来源事实；
- 镜头时长为 500～15000ms 且使用 500ms 粒度；
- 每个 Beat 至少一个镜头；
- 单镜字段完整、模型输出可被严格解析；
- ReviewArtifact、任务、Head、CAS 和正式版本事务一致。

### 6.2 非阻断评估

以下内容只能形成发现，不能由代码直接改写镜头或拒绝候选：

- 新场景是否需要空间交代；
- 平均镜头时长、慢镜比例和单集时长；
- 景别或运镜是否单调；
- 相邻镜头是否重复；
- 是否缺少有意义的非对白镜头；
- 轴线、视线、屏幕方向、动作和情绪连续性；
- 镜头是否适合即梦稳定生成；
- 补充镜头是否真的有叙事职责。

Reviewer 只有在核心情节目标未落实、与原文矛盾、时间线无法理解或镜头明显不可执行时，才要求 Agent 自动完整返工一次。返工后仍存在问题时也要把候选和发现交给用户，不再让整个任务稳定失败。

## 7. 正式方案修订

`POST /api/v1/video/chapter-adaptations/{adaptationId}/shot-plan-runs` 增加：

- 可空 `baseShotPlanVersionId`；
- 可空 `revisionBrief`；
- 有基线时必须等于当前 Head 的正式方案。

Core 把当前正式方案完整冻结进 `ChapterAdaptationPlanJobPayload.baseShotPlan`。Agent 重新分析原文覆盖目标，并在设计阶段参考基线：保留仍有明确作用的镜头，允许重新分场、合并、拆分、调整声音或替换重复镜头，但必须返回完整方案。

任务 `baseShotPlanVersionId` 记录来源版本。用户确认后创建新的 `VideoShotPlanVersion`，其 `basedOnVersionId` 来自任务基线；旧版本、旧镜头和旧提示词都不修改。新的 ShotPlan 会清空当前 EpisodePlan 指针，提示词需要基于新镜头重新确认。

## 8. Agent 工作流

```text
分析 Scene / Beat / CoverageGoal
  → Core 保存 dramatic_structure checkpoint
  → 结合可选正式基线按闭合 beatsByKey 生成完整镜头候选
  → 用精确 U 来源归属纠正旧 Beat 编号错位，仅补全仍然缺失的 Beat 槽
  → 仅执行结构硬校验并收集确定性提示
  → Reviewer 输出决策与审镜发现
  → 必要时最多一次完整返工
  → 带初审发现的 ReviewArtifact
```

物化阶段禁止再强行修改新场景首镜的 `narrativePurpose`、`shotScale` 或 `cutReason`。Prompt 任务读取 `storyFunction`、`audienceGain`、对白和声音分层，但仍不得改变已确认镜头边界。

模型的 Beat 槽、来源 U 和目标 G 不是同一信任等级：U 由第一阶段 checkpoint 固定，若镜头整体沿用旧基线 Beat Key，
Agent 按 U 与 Beat 的精确集合归属把草案移动到正确槽位，不使用自然语言首次位置猜测；移动后仍缺失的 Beat 才发起
一次只包含缺失槽的小型补全，不重写已经完成的镜头。跨 Beat 的 G 只属于可编辑软元数据，进入正式候选前剔除并
形成审镜提示；跨 Beat 的 U 不得进入候选，无法保留合法来源的直呈/推导镜头降为视听补充并提示作者核对。

逐镜提示词仍只接受严格 `ShotPromptSpec`。模型只读取目标镜头自己的 Scene、Beat、正式 Shot、来源范围和本镜相关的
冻结设定；当前镜头事实覆盖具体设定，具体设定覆盖全局风格，动态道具状态不得脱离本镜来源进入动作。
不再接收完整章节正文或前后镜完整画面，避免把邻镜事件重新演进当前镜头。真实供应商第一次返回非 JSON、混入正文、
缺少结构化对象或没有通过时长/景别/编译门禁时，同一任务内允许追加一次带具体原因的 JSON Schema 纠正要求并重新
调用；第二次仍有结构、目标顺序、编译或预算硬错误则任务失败，只有语义质量问题则带 `qualityWarnings` 形成待审候选。
不得无限重试、从可见正文猜 JSON、保存半截提示词，或因纠正调用覆盖已有正式
PromptVersion。Agent 必须在完成回调前按正式画幅和时长实际编译每个候选，不能出现任务已完成但 Core 无法展示候选。

## 9. 前端原型

沿用现有章节影视化三栏工作台：

- 左栏：冻结原文和镜头来源映射；
- 中栏：Scene → Beat → CoverageGoal → Shot 时间线；
- 右栏：镜头作用、观众获得、目标绑定、来源关系、摄影、对白和声音。

正式方案状态下提供“基于 vN 生成修订候选”，并允许输入可选修订重点。待审候选顶部展示 AI 初审摘要和非阻断发现；节拍目标实时显示“已覆盖/未覆盖”。确认按钮不因非阻断发现禁用，但提交前仍执行严格 API 契约校验。

界面继续遵循 `DESIGN.md`：PC 三栏、hairline 边框、紧凑列表、克制状态色、原生 CSS，不新增营销式页面或大卡片群。

## 10. 开发库迁移

只修改并重新执行已批准的具名开发迁移：

`scripts/migrations/20260818_video_chapter_adaptation_domain.sql`

目标数据库必须是 `novelwriterdev`。迁移：

- 放宽 `VideoAdaptationTask` 的 shot_plan 基线约束；
- `VideoDramaticBeat` 增加可空兼容列 `coverageGoalsJson`；
- `VideoShot` 增加可空兼容列 `sourceRelation/storyFunction/audienceGain/coveredGoalKeysJson/speechMode/spokenText`；
- 既有正式 v1 行保持原值，不删除、不覆盖；读模型为旧行提供明确的兼容投影；
- 新正式版本必须写入全部新列。

迁移后只读导出 `schema-contract.json`，不得连接生产数据库，也不得让应用启动执行 DDL。

## 11. 验收标准

1. 服务端不再改写首镜目的、景别和切镜理由。
2. 首镜不是建立镜头、平均时长超经验区间或存在慢镜时，候选仍可进入人工审核。
3. 新候选每个 Beat 有覆盖目标，每个生成镜头有本镜作用和观众获得。
4. 用户可以看见未覆盖目标、重复镜头等建议，但仍拥有最终确认权。
5. 对白位置和环境声可以同时表达，画外对白不会再被存成纯环境声。
6. 正式 v1 可作为任务基线；确认修订后产生 `basedOnVersionId=v1` 的 v2，v1 行不变。
7. Agent 第二轮仍未完全通过时返回带 warning 的候选，不把任务直接判失败。
8. 大对象输出遗漏 Beat 时只补全缺失槽；模型沿用旧 Beat Key 时可由 U 精确归属纠正，不生成重复尾声。
9. 逐镜提示词读取新的职责、来源与声音字段。
10. 公共 OpenAPI 客户端重新生成，前端不手写 DTO。
11. 相关 Web、Core、Agent、service-contracts 测试、TypeScript 类型检查、Lint、Ruff 和 Mypy 通过。
12. 只在 `novelwriterdev` 应用迁移并通过 schema guard；本地浏览器能从正式 v1 启动修订并看到待审候选。
13. 逐镜提示词首次结构化输出无效时只纠正一次，成功后仍是未保存候选，连续失败时明确收敛为失败。
14. 新提示词候选按镜头内容选择性提交 `expressionAndGaze`；物件/无人镜头为空，全景不含微表情，同一服装、场景、
    动作不在多个字段机械重复。
15. 新模型不再提交 `performance/continuity`；历史候选仍可读取和编译。
16. 目标镜头上下文不包含完整章节或前后镜完整事件；邻镜剧情不得进入当前镜头提示词。
