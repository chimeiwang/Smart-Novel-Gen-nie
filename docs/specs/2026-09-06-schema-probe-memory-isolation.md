# 运行中 Core 的结构检查进程隔离

状态：仓内、隔离实测及当前生产版本的只读复验通过；仅修复发布与迁移检查方式，不改变业务接口、数据库结构或发布授权。

## 现场依据

2026-09-06 发布前检查时，生产仍运行 `a37d873`。在其 448 MiB Core 容器内执行现有
`inkforge-schema-guard` 会额外启动 JVM，并继承服务的 JVM 配置。该次检查返回 137，内核记录同一
容器的内存超限；Core 自动重启计数由 0 增为 1。随后六项 readiness 检查全部恢复通过。
这是检查方式引入的影响，不能把数据库查询只读等同于运行过程没有资源风险。

## 最小修复

- 结构检查改在有独立内存、CPU、进程数和时间上限的一次性容器中运行，不再向活动 Core 容器增加 JVM。
- 使用现场 Core 的完整容器 ID 与不可变镜像 ID，复用其网络命名空间，以同一镜像契约和同一数据库配置
  做实时检查；不按可能已变化的 tag 猜版本，不启动第二个业务 Core 或后台 worker。
- 只传递结构检查实际需要的数据库地址、视频与手机号三个配置开关；不继承服务的 JVM 参数、JWT、
  模型密钥或服务私钥。凭据通过受保护临时文件传递，不进入参数、标准输出或错误日志。
- 调用原 SchemaGuardCommand，保留精确结构比较、能力投影、单行指纹及失败退出语义，不能用缓存的
  readiness 或固定 contract 指纹代替实时校验。
- 检查前后核对目标 Core 仍是同一运行实例、同一镜像，未重启；不满足即失败。探针失败不能触发
  重启业务服务或放宽 schema guard。始终清理本次探针及临时凭据，不接触其他容器或卷。
- 部署、V2 迁移/发布门禁与回滚演练统一使用此入口，不建立额外发布控制面。
