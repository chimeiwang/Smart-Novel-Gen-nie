# 正文写作各项 token 预算统一为十万

日期：2026-09-11。状态：实施中。用户在确认推理 8,627 超过 8,000 导致新任务失败后，明确要求“统统改成10万”。

## 目标与范围

- `long_serial.write_chapter` 的生成、两类复审采用新的 v3 Step 预算：输入、冷缓存输入、总输出、推理、可见输出五项上限均为 100,000。
- Run 采用 `budget.long_serial.chapter_draft.v3`，五项累计 token 上限均为 600,000，覆盖现有最多六次调用。
- 总输出包括推理与可见输出，其 100,000 是共同硬上限；两个分项的额度分别是上限，不表示预分配份额。
  Python 契约、Registry 和 Java 领域校验统一为各分项不大于总额度；实际用量的总量一致性与超额拒绝继续执行。
- 推理开关由 model profile 决定。关闭推理的复审可以持有相同 token 上限，但仍发送 thinking disabled；开启推理的 profile 仍要求正推理额度。
- 保留 v1/v2 资产及所有已冻结任务的精确预算，旧任务首次派发后续复审、返工与恢复均不得自动扩大。
- 不改变费用、耗时、重试、调用次数、模型选择、目标篇幅、其他操作或数据库结构。

## 验收与发布

- 回放实际输入 31,742、推理 8,627、总输出 11,406、可见输出 2,779，合法完整响应可进入候选及双复审。
- token 上限 100,000 可用，100,001 拒绝；实际输出拆分仍必须匹配总输出，不允许将两项各自十万变成二十万总输出。
- 测试 v1/v2 冻结预算继续生效，双复审保持推理关闭，Run 预算覆盖新 Step。
- 通过完整 GitHub CI 和 deploy 作业；在镜像和源码上传完成、部署即将开始前，才临时关闭新建写作入口，权威非终态 V2 Run 数为零才切换 manifest。
- 部署后恢复原路由，验证三服务版本、健康、Core/Agent 资产与各项 token 上限，明确旧任务需要新建才采用新额度。

本规格取代 [输入预算调整](2026-09-11-chapter-writing-input-budget.md) 中新 Run 的 v2 额度选择，保留其历史冻结要求。
发布继续使用 [独立生产热修复](2026-09-11-chapter-writing-budget-production-hotfix.md) 的生产基线和发布分支。
